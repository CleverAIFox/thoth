# thoth — 결정 기록

> **같은 실수를 두 번 하지 않으려고 적는다.** 무엇을 정했는지가 아니라
> **무엇을 배웠는지**가 이 문서의 목적이다. 결과만 남는 것은 `MASTER.md`,
> 앞으로 할 일은 `PLAN.md` 에 있다.
>
> **append-only.** 이미 적힌 절은 고치지 않는다. 판단이 뒤집히면 새 절을
> 추가하고 옛 절에서 그리로 연결한다.
>
> 절 번호는 커밋 메시지가 인용한다. 지우거나 다시 매기지 않는다.
>
> 각 절은 **증상 → 원인 → 조치 → 배운 것** 순서로 적는다. "배운 것" 이 없으면
> 그 항목은 여기 올 자리가 아니다.

## §1. DOM 노드가 늘어나면 인덱스 기반 수집은 깨진다

**2026-09-12**

### 증상

선행 저장소의 수집 코드가 `document.querySelectorAll(RICH_TEXT)` 로 긁어
`[0]` 을 문제, `slice(1)` 을 보기로 잘랐다. 사전 조회 방식에서는 매칭이 실패해도
아무것도 붙지 않아 조용히 지나갔다.

### 원인

Udemy 는 채점 후 해설 노드를 같은 셀렉터로 **보기 사이에** 끼워 넣는다.
실측하니 5개에서 9개로 늘었고 순서가 문제 · 보기1 · 해설1 · 보기2 · 해설2 …
였다. `slice(1)` 은 채점 후 인덱스 2를 보기2로 취급한다.

실시간 번역으로 바꾸면 **조용한 실패가 시끄러운 오답으로 바뀐다.** 1번 보기
자리에 2번 번역이 붙는다. 학습 도구에서 이것은 없는 것보다 나쁘다.

### 조치

수집을 인덱스가 아니라 **요소 자체**로 한다. 문제 · 보기 · 해설이 각각 고유
id 를 갖는 것을 정찰에서 확인했으므로 id 로 직접 질의한다. 순서가 어떻게
섞여도 무관해진다. 계약은 MASTER §3.

### 배운 것

**정찰 30분이 오역을 막았다.** 실시간 전환 전에 채점 전후 DOM 을 둘 다 떠본
것이 결정적이었다. 한쪽만 봤으면 반대쪽에서 통째로 놓쳤다.

그리고 **동적으로 노드가 늘어나는 DOM 에서 인덱스는 식별자가 아니다.** 이것은
Udemy 만의 문제가 아니라 모든 사이트에 해당한다. 제네릭 계층도 인덱스가 아니라
요소 순회로 설계한다.

## §2. 프로세스 메모리에 둔 카운터는 Lambda 에서 무효다

**2026-09-12**

### 증상

월 문자 상한을 지키는 `guard.py` 를 모듈 전역 `_used` 로 구현했다. 로컬에서는
정확히 동작했다.

### 원인

Lambda 는 콜드스타트마다 프로세스가 새로 뜨므로 전역 변수가 0 으로 리셋된다.
동시 실행되면 인스턴스마다 따로 센다. **배포하는 순간 상한이 사실상 걸리지
않는다.**

읽고-판단하고-쓰는 순서도 문제였다. 두 요청이 같은 잔여를 보고 둘 다 통과한다.

### 조치

카운터를 DynamoDB 로 옮기고 `ConditionExpression` + `ADD` 로 조건부 원자 증가를
쓴다. 판단과 증가가 한 연산이라 경쟁이 없다. 그리고 **번역 전에 예약**한다.
실패 시 과다 계상되지만 과소 계상보다 안전하다.

### 배운 것

**로컬에서 완벽히 동작하는 코드가 실행 환경 때문에 무용지물이 될 수 있다.**
문법도 로직도 틀리지 않았고, 서버리스의 실행 모델을 알아야만 보이는 종류의
결함이다.

판단 기준이 생겼다. **상태를 어디에 두는가**를 먼저 묻는다. 캐시를 브라우저에
두면 사용자마다 재과금이고, 카운터를 프로세스에 두면 인스턴스마다 리셋이다.
이 프로젝트에서 어려웠던 것은 로직이 아니라 전부 이 질문이었다.

## §3. 파일시스템 경계를 넘는 I/O 는 값이 비싸다

**2026-09-12**

### 증상

모델 파일을 SSD(`/mnt/f`)에 두도록 `OLLAMA_MODELS` 를 설정했다. 2.4GB 모델의
첫 로딩에 **2분 12초**가 걸렸다.

### 원인

`/mnt/f` 는 DrvFs 다. Windows 파일시스템을 번역 계층을 통해 읽으므로 대용량
순차 읽기에서 네이티브 ext4 와 차이가 크다. 경로 선택의 문제가 아니라
파일시스템 경계의 문제다.

hathor D-0120(`copy2` 가 DrvFs 에서 `chmod` 로 죽는다)과 같은 계열이다.
`rsync -a` 도 `-p` 를 포함해 같은 이유로 실패한다.

### 조치

모델을 `~/.ollama`(ext4)로 되돌렸다. 그리고 **WSL 배포판 자체를 F: 로 이전**했다
(`wsl --manage --move`). vhdx 가 SSD 에 있으면서 내부는 ext4 네이티브라 두
목표를 모두 만족한다.

확장 동기화는 DrvFs 를 피할 수 없다(크롬이 네트워크 경로에서 압축해제 확장을
로드하지 못한다). 그래서 권한 보존을 끈 `rsync -rlt --no-perms --no-owner
--no-group` 을 쓴다.

### 배운 것

**"SSD 라서 빠르다" 는 파일시스템을 건너뛴 판단이다.** 물리 매체가 아니라
접근 경로가 속도를 정한다.

그리고 **DrvFs 를 피할 수 없는 경우와 피할 수 있는 경우를 나눠야 한다.**
모델 로딩은 피할 수 있고(ext4 로 옮기면 된다), 확장 로드는 피할 수 없다
(크롬 제약). 후자는 우회하지 말고 제약에 맞춰 옵션을 조정한다.

## §4. 파라미터로 모델의 성격을 이길 수 없다

**2026-09-12**

### 증상

`qwen3:4b` 에 `"think": false` 를 넘겼는데 무시했다. 번역 한 줄을 뽑으려고
수천 토큰짜리 사고를 돌렸고 **1분 28초**가 걸렸다. 출력에 `</think>` 가 그대로
찍혔다.

### 원인

qwen3 는 추론 모델이다. 사고 과정이 부가 기능이 아니라 동작 방식이라
파라미터로 끄는 것이 싸움이 된다. 번역은 추론이 필요 없는 작업인데 매번 값을
치르고 있었다.

### 조치

비추론 모델인 `exaone3.5:7.8b` 로 교체했다. 같은 작업이 2.7초다. 진 모델은
즉시 삭제하고 `doctor.sh` 가 미채택 모델을 FAIL 로 보고하도록 했다.

### 관련 발견 둘

**비결정성.** `temperature 0.2` 에서 같은 입력에 다른 출력이 나왔다. 한 번은
"접근 불가능하게 만듭니다", 다음은 "접근할 수 없게 합니다". 캐시가 최초 결과를
영구 고정하므로 흔들린 결과가 그대로 박제된다. `temperature 0` + 고정 seed 로
같은 출력을 확인했다. **결정성을 모델이 아니라 캐시가 보장하지만, 캐시에 들어갈
값이 옳은지는 별개 문제다.**

**조사 누락.** 서비스명을 영어로 두라고만 지시하니 뒤에 한국어 조사가 붙지
않아 비문이 됐다("Kinesis Data Streams 거의 즉시…"). 조사 부착을 예시와 함께
명시하니 해결됐다. 규칙 하나가 다른 규칙의 부작용을 만든다.

**답 생성.** 긴 지문에서 모델이 번역을 마친 뒤 스스로 답을 이어 붙였다. 문풀
도구에서는 정답 누설이고, 지어낸 답이 사실과 반대이기까지 했다. 프롬프트 규칙을
추가해 줄였으나 완전히 없애지 못했다(PLAN §2-2).

### 배운 것

**작업에 맞는 모델을 고르는 것이 파라미터 조정보다 먼저다.** 모델 선택이 틀리면
파라미터로 되돌릴 수 없다.

그리고 **프롬프트 규칙은 서로 간섭한다.** 규칙을 추가할 때마다 이전 규칙의
결과가 달라지는지 확인해야 한다. 이것이 골든셋이 필요한 이유다.

## §5. 휘발성 캐시는 재시작마다 재과금이다

**2026-09-12**

### 증상

`CACHE=memory` 로 개발하던 중, 코드를 고칠 때마다 워커가 재시작되면서 캐시가
비었다. 한 페이지 9개를 매번 처음부터 번역했다.

### 원인

로컬 엔진이라 비용은 시간뿐이었지만, **과금 엔진이었으면 재시작 한 번이 곧
재과금**이다. 선행 저장소에서 스크래핑 크래시로 재실행할 때마다 AWS Translate
비용이 다시 나갔던 것과 정확히 같은 구조다.

### 조치

`CACHE=file` 모드를 추가해 개발 중에도 영속 캐시를 쓴다. 배포에서는 `ddb` 다.

### 배운 것

**캐시의 영속성은 개발 편의가 아니라 비용 방어책이다.** "개발 중이니까 메모리로
충분하다" 는 판단이 배포 시점의 구조를 그대로 결정했을 수 있다.

그리고 **캐시를 어디에 두느냐가 비용 모델을 정한다.** 브라우저면 사용자마다,
프로세스면 재시작마다, 서버면 한 번이다. 선행 저장소의 `chrome.storage.local`
캐시는 사용자 10명이면 같은 문장을 10번 번역하는 구조였다.

## §6. 짧은 샘플로 잰 레이턴시는 실사용을 대표하지 않는다

**2026-09-12**

### 증상

`exaone3.5:7.8b` 벤치마크에서 2.7초가 나와 로컬 엔진 채택을 결정했다. 실제
페이지에 붙이니 **3~4분**이 걸렸다.

### 원인

벤치 문장의 출력이 26토큰이었다. 실제 문제 지문과 해설은 한국어 출력이 300토큰
가량이다. ollama 로그에 답이 있었다.

```
eval time = 2551.83 ms / 26 tokens (102.07 ms per token, 9.80 tokens per second)
```

**토큰당 시간이 지표였는데 총 시간을 봤다.** 10 tok/s × 2,700토큰 = 270초.
계산하면 나오는 값이었다.

### 조치

벤치 도구가 실제 길이의 샘플을 쓰도록 바꾸고, 실측값을 MASTER §7-1 에 토큰당
속도로 기록한다. 로컬 엔진은 실사용 불가 판정하고 호스팅 API 로 전환한다.

### 배운 것

**생성 모델의 레이턴시는 출력 길이에 비례한다. 단일 측정값이 아니라 처리율로
재야 한다.** 벤치 샘플이 실제 워크로드를 닮지 않으면 측정 자체가 거짓말이 된다.

로컬 엔진을 지우지는 않는다. 오프라인 개발용이자 비교 기준선이고,
"소비자 GPU 로는 이 워크로드가 안 된다" 는 판단의 근거 자체가 자산이다.

## §7. NMT 와 LLM 은 다른 물건이다

**2026-09-12**

### 증상

"구글 번역기는 가볍고 즉시 응답하는데 왜 이것은 4분인가" 라는 의문이 생겼다.

### 원인

구글 번역과 AWS Translate 는 LLM 이 아니라 **NMT**(신경망 기계번역) 전용
모델이다. 번역만 하는 인코더-디코더 구조이고 파라미터가 수십~수백 배 작으며,
시스템 프롬프트를 매번 처리하지 않는다.

`ENGINE=translate` 가 즉시 응답했던 것이 그 증거였다. **선행 저장소의 구조는
이미 빨랐다.**

LLM 으로 옮긴 이유는 품질이었다. NMT 는 지시를 받지 못해 "Kinesis Data
Streams" 를 "Kinesis 데이터 스트림" 으로 뭉갠다. 서비스명 보존에 AWS Custom
Terminology 같은 별도 장치가 필요하고, 그것은 AWS 전용이라 이식되지 않는다.

### 조치

품질을 택하고 속도는 하드웨어로 해결한다. 같은 모델을 데이터센터 GPU 에서
돌리면 처리율이 열 배 이상이다. **모델을 바꾸는 것이 아니라 실행 위치를
바꾸는 것**이므로 품질을 잃지 않는다.

`engine.py` 를 3분기 구조로 둔 덕분에 함수 하나 추가로 끝난다.

### 배운 것

**4분은 결함이 아니라 품질을 위해 치른 값이었다.** 원인을 "느린 코드" 로 보면
최적화할 곳을 찾게 되는데, 실제로는 교환 관계였고 지불 수단을 바꾸면 되는
문제였다.

그리고 **엔진을 환경변수로 교체 가능하게 만들어 둔 것이 이 판단을 싸게
만들었다.** 세 엔진을 같은 인터페이스에 꽂아 두었기에 비교가 가능했고, 비교가
가능했기에 근거를 갖고 고를 수 있었다.

## §8. 용어집은 커버리지가 아니라 재발 방지 장치다

**2026-09-12**

### 증상

같은 페이지 안에서 `record` 가 지문에서는 "기록", 정답에서는 "레코드" 로
번역됐다. 용어집을 도입하려 하니 "커버하지 못하는 용어가 나오면 어떻게
하는가" 라는 문제가 걸렸다.

### 원인

두 문제가 섞여 있었다.

**일관성**은 항목마다 개별 호출해 모델이 앞 문장을 모르기 때문이다. 배치
번역으로 구조가 해결한다.

**표기 선택**은 AWS 한국어 문서 관행("레코드")과 맞추는 문제다. 이것만 용어집의
몫이다.

### 조치

두 층으로 나눴다. **보편 규칙**(고유명사 유지 · 조사 부착 · 내용 추가 금지)은
프롬프트에 고정하고 도메인 지식이 0 이다. **도메인 용어집**은 JSON 파일이고
없어도 번역이 동작한다.

도메인 판정은 코드가 하지 않는다. 모든 용어집을 훑어 **원문에 실제로 나타난
용어가 가장 많은 것**을 고른다. 새 도메인은 JSON 추가로 끝난다.

### 배운 것

**룰 기반으로 100% 를 목표하면 설계가 망가진다.** 커버리지를 목표로 두면
용어집이 무한히 커지고 도메인 전용 도구가 된다.

목표를 바꿨다. **용어집은 "이미 발견한 오류의 재발 방지" 다.** `record → 기록`
을 눈으로 발견했으므로 등재했고 다시 나오지 않는다. 아직 문제되지 않은 용어는
모델 판단에 맡긴다.

그래서 **검증 가능한 불변식이 생긴다.** "등재 용어의 위반 0" 은 골든셋으로
측정되지만 "번역 정확도 100%" 는 측정 자체가 불가능하다. 측정할 수 없는 목표는
세우지 않는다.

미등재 용어의 커버리지는 사후에 자란다. 콜드패스가 실제 번역된 텍스트에서 빈출
용어를 뽑아 후보를 주고, **사람이 승인해서** 등재한다. 자동 반영하지 않는 이유는
잘못된 번역이 스스로를 강화하기 때문이다.

## §9. 세션이 바뀌는 작업은 단독 작업이 아니다

**2026-09-12**

### 증상

문서 강제자를 두지 않기로 했다. 근거는 "단독 작업이라 리뷰어가 작성자 자신"
이었다. 그런데 같은 날 `⬛` 표기 규약을 두 번 어겼다. 해결된 항목의 내용을
PLAN 에 남겨 MASTER 와 중복시켰고, 사람이 지적해서야 고쳤다.

### 원인

전제가 틀렸다. 문서를 쓰는 주체가 여러 세션에 걸쳐 있고, **세션이 바뀌면 문맥이
초기화된다.** 규약을 기억하는 주체가 연속되지 않으므로, 실제로는 여러 손이 같은
문서를 업서트하는 상황이다. 그것이 강제자가 존재하는 조건 자체다.

### 조치

`tools/check_docs.py` 를 두고 `doctor.sh` 가 부른다. 1·2인칭, 경어체 종결,
대화체 표현, DECISIONS 절의 "배운 것" 유무와 번호 연속성을 검사한다.
fire-lane 의 검사 30여 종을 옮기지 않고 문체·구조 한 종만 둔다. 규모에 맞지
않는 강제자는 유지 비용이 얻는 값을 넘는다.

검사 대상은 형식뿐이다. 내용의 옳고 그름은 사람이 본다.

### 배운 것

**"단독 작업" 의 기준은 사람 수가 아니라 문맥의 연속성이다.** 혼자 쓰더라도
작업 사이에 기억이 끊기면 협업과 같은 실패가 난다. 오랜 공백을 두고 돌아오는
프로젝트에도 같은 판단이 적용된다.

그리고 **규약을 문서에 적는 것만으로는 지켜지지 않는다.** 머리말에 규칙을
써 두었는데도 어겼다. 적는 것과 지키는 것은 다른 일이고, 지키는 쪽은 도구의
몫이다.

## §10. 기본 설정으로 돌지 않는 코드를 테스트가 가렸다

**2026-09-12**

### 증상

워커 테스트 8개가 전부 통과했다. 그런데 `.env.example` 그대로 띄우면
`/health` 와 `/translate` 가 AWS 로 나갔다. 로컬 개발에 AWS 호출이 있을
이유가 없다.

### 원인

`guard.py` 가 백엔드를 `MODE = os.environ.get("CACHE", "memory")` 로 정하고
`MODE == "memory"` 냐 아니냐로 갈랐다. `CACHE` 는 `memory` · `file` · `ddb`
세 값인데 이분법으로 가른 것이다. 현재 값인 `CACHE=file` 은 "memory 가 아님"
이므로 DynamoDB 경로로 떨어졌다.

테스트는 맨 위에서 `os.environ["CACHE"] = "memory"` 로 덮었다. **기본값이
아닌 유일한 값으로만 검증하고 있었다.** 통과한 8개는 이 결함을 구조적으로
볼 수 없었다.

여기에 두 번째 층이 겹쳤다. `main.py` 는 `QuotaExceeded` 와 `TooLong` 만
잡는다. 자격증명 없음은 그 둘이 아니므로 500 으로 흘렀고, 예외가 미들웨어를
건너뛰어 CORS 헤더가 빠졌다. §2 에 적어 둔 실패 모드가 그대로 재현됐다.

### 조치

백엔드 판정을 `REMOTE = MODE == "ddb"` 로 뒤집는다. 원격은 하나뿐이고 나머지는
로컬이라고 적는 쪽이 값이 늘어도 안 깨진다.

`file` 모드는 카운터도 파일에 남긴다. 메모리에 두면 재시작마다 월 사용량이
0 이 되어 상한이 무의미하다. 캐시와 같은 이유다(§5).

저장소에 닿지 못하는 경우를 `GuardUnavailable` 로 따로 세우고 503 으로
돌려준다. **세지 못하면 번역하지 않는다.** 통과시키면 상한이 없는 것과 같다.

테스트에 `guard.REMOTE is (guard.MODE == "ddb")` 와 file 모드 영속성을
넣었다.

### 배운 것

**열거값을 이분법으로 가르면 값이 셋이 되는 순간 조용히 틀린다.** 틀린 쪽이
기본값이면 아무도 안 밟는 경로가 아니라 모두가 밟는 경로가 된다.

그리고 **테스트가 기본 설정을 건드리지 않으면 기본 설정은 검증된 적이 없는
것이다.** 테스트를 결정적으로 만들려고 환경을 고정하는 것은 옳지만, 고정한
값이 아무도 쓰지 않는 값이면 그 테스트는 제품이 아니라 테스트 자신을 검증한다.

세 번째로 **"이미 배웠다" 와 "막았다" 는 다르다.** §2 에 CORS 오인 실패 모드를
적어 두고도 같은 실패 경로를 새로 열었다. 배운 것을 문서가 아니라 코드에
박아야 한다. 여기서는 에러 응답에 CORS 헤더가 붙는지 보는 테스트다.

## §11. 배타 선택 구조에서 상위 계층은 하위 계층보다 나빠질 수 있다

**2026-09-12**

### 증상

`standard` 어댑터가 걸린 페이지에서 보기만 번역되고 문제 지문과 본문이
통째로 빠졌다. `generic` 만 있을 때는 나왔던 것이다.

### 원인

브로커가 `priority` 내림차순으로 정렬해 `find` 로 **하나만** 고른다.
`standard` 는 `priority` 5 로 `generic` 을 이기는데, `collect` 는
`[role=radiogroup]` 안의 보기만 모은다. 이기는 순간 나머지가 사라진다.

계층을 "정확도를 높이는 장치" 로 설계했는데, 선택이 배타적이면 상위 계층은
**덧붙이는 것이 아니라 대체하는 것**이다. 설계 의도와 실행 구조가 어긋났다.

### 조치

`generic` 의 수집 로직을 `ST.genericCollect(root, {skip})` 로 꺼내
`standard` 가 자기 몫을 모은 뒤 나머지를 위임하게 했다. 상위 계층이 하위
계층을 덮지 않고 얹는다.

같이 고친 것이 하나 있다. `[role=radio]` 와 `label` 을 함께 질의하면 서로를
감싸는 쌍에서 같은 텍스트가 두 번 잡힌다. 다른 후보를 품은 요소는 버린다.

### 배운 것

**"폴백" 이라는 말이 구조를 보장하지 않는다.** Layer 0 이 항상 참이면 어디서나
동작한다는 주장은 Layer 0 이 실제로 선택될 때만 참이고, 배타 선택에서는 상위
계층이 있을 때 거짓이 된다.

판단 기준이 생겼다. **계층을 쌓을 때 선택이 배타적인지 가산적인지 먼저
정한다.** 배타라면 상위 계층은 하위 계층의 상위집합이어야 한다. 그 조건을
지킬 수 없으면 선택이 아니라 합성으로 간다.

## §12. 실패를 잊는 재시도는 재시도가 아니라 폭주다

**2026-09-12**

### 증상

번역이 실패한 자리에서 워커로 같은 요청이 1.5초마다 끝없이 나갔다.

### 원인

브로커의 `drop` 이 삽입한 박스를 걷으면서 `el.dataset.stDone` 을 지웠다.
중복 수집을 막는 표시가 사라지므로 다음 순회가 같은 유닛을 새 것으로 보고
다시 보낸다. `setInterval` 이 1.5초마다 돈다.

재시도 자체가 틀린 것은 아니다. **실패의 종류를 구분하지 않은 것**이 틀렸다.
429 상한 초과와 413 길이 초과는 같은 입력으로 다시 보내도 결과가 같다. 재시도가
상황을 바꾸지 못하는데 횟수 제한도 없었다.

실제 사용 조건에서 이것은 이론이 아니다. 5,000자를 넘는 요소가 페이지에 하나만
있어도 그 하나가 영구히 워커를 때린다.

### 조치

실패를 영구와 일시로 가른다. 클라이언트가 상태 코드를 실은 오류를 던지고,
4xx 는 영구로 본다. 영구 실패는 `dataset.stFail` 로 표시해 이 세션에서 다시
건드리지 않고, 일시 실패는 두 번까지만 재시도한다.

`quota_exceeded` 와 `guard_unavailable` 은 페이지 단위 문제가 아니므로 순회
자체를 멈춘다. 관측자와 타이머를 끊는다.

순회가 겹치지 않도록 `running` 잠금도 걸었다. `run` 이 비동기인데 타이머와
관측자가 각각 부르면 같은 배치가 두 번 나갈 수 있다.

### 배운 것

**멱등성 표시를 실패 경로에서 지우면 멱등성이 사라진다.** `stDone` 은 "처리
완료" 가 아니라 "이미 봤다" 는 뜻이어야 했다. 결과가 성공이든 실패든 본 것은
본 것이다.

그리고 **재시도를 넣을 때 종료 조건을 같이 넣지 않으면 그것은 재시도가 아니라
루프다.** 클라이언트가 상태 코드를 버리고 문자열 메시지만 던지고 있었기 때문에
브로커는 구분할 재료조차 없었다. **판단에 필요한 정보를 경계에서 버리지
않는다.**

## §13. 비동기 대기는 사용자 제스처를 끊는다

**2026-09-12**

### 증상

Udemy 외 사이트에서 아이콘을 눌러도 권한 요청 창이 뜨지 않았다.

### 원인

`chrome.permissions.request` 는 사용자 제스처 안에서 불려야 한다. 코드가
`chrome.permissions.contains` 를 먼저 `await` 하고 그 결과로 `request` 를
불렀다. 대기 한 번에 제스처 문맥이 끝나 요청이 거부된다.

`contains` 는 애초에 필요 없었다. 이미 가진 권한이면 `request` 가 창을 띄우지
않고 곧바로 참으로 해소된다.

### 조치

`request` 를 제스처 직후 첫 호출로 옮기고 `contains` 를 뺐다. 주입 실패도
같이 감쌌다 — `chrome://` · 웹스토어 · 파일 URL 은 주입이 막혀 있는데 잡지
않으면 서비스 워커 콘솔에 오류로 쌓인다.

`ST_STATIC` 의 정규식도 좁혔다. `/(^|\.)udemy\.com$/` 는 `www` 가 아닌
호스트까지 건너뛰는데 `content_scripts` 는 `www.udemy.com` 만 맡는다. 양쪽이
어긋나면 아무도 안 맡는 구멍이 생긴다.

### 배운 것

**확인을 먼저 하는 습관이 여기서는 기능을 껐다.** 방어적으로 상태를 조회하고
분기하는 것이 일반적으로는 옳지만, 호출 자체에 시간 제약이 걸린 API 에서는
조회가 비용이 아니라 실패 원인이다.

그리고 **한 가지 사실을 두 곳에 적으면 어긋난다.** manifest 의 매치 패턴과
배경 스크립트의 제외 목록이 같은 사실을 다른 문법으로 적고 있었다. 지금은
주석으로 묶어 두었지만, 구조적으로는 한쪽에서 읽어 쓰는 쪽이 옳다.

## §14. 방어적 문법이 실패를 숨겼다

**2026-09-12**

### 증상

Udemy 외 사이트에서 아이콘을 눌러도 권한 창이 뜨지 않았다. §13 에서 이미
한 번 고쳤는데도 그대로였다. 서비스 워커 콘솔에는 아무것도 찍히지 않았다.

### 원인

`chrome.action.onClicked` 리스너의 첫 줄이 이랬다.

`if (!tab.id || !tab.url?.startsWith("http")) return;`

오리진 권한이 없는 탭의 `tab.url` 은 `undefined` 로 온다. 확장은 권한 없는
탭의 URL 을 볼 수 없다. 그래서 이 줄에서 곧바로 되돌아갔고 권한 요청까지
가지도 않았다.

**닭과 달걀이다.** 권한을 요청하려면 대상 오리진을 알아야 하는데, 오리진을
보려면 권한이 있어야 한다. `activeTab` 이 이 고리를 끊는다 — 아이콘 클릭
순간 그 탭에 한시적 접근이 생긴다.

진단이 오래 걸린 이유는 문법이다. `tab.url?.startsWith` 의 옵셔널 체이닝이
`undefined` 를 조용히 흡수했다. `tab.url.startsWith` 였다면 TypeError 가
콘솔에 찍혀 첫 클릭에 드러났을 것이다. 대신 "리스너는 등록돼 있는데 아무
일도 일어나지 않는다" 는, 가장 진단하기 어려운 상태가 됐다.

### 조치

`permissions` 에 `activeTab` 을 넣었다. 그리고 되돌아가는 분기마다 무엇이
없는지 남긴다. 조용히 끝내지 않는다.

같이 정리한 것이 있다. Udemy 만 `content_scripts` 로 자동 주입하던 특별대우를
없앴다. 같은 사실이 `host_permissions` · `matches` · `ST_STATIC` 세 곳에 서로
다른 문법으로 살았는데, 모든 사이트가 같은 경로를 타게 하니 셋이 다 사라졌다.
**저장소에 사이트 목록이 없어졌다.**

### 배운 것

**옵셔널 체이닝은 값이 없을 수 있는 곳에 쓰는 것이지, 없으면 안 되는 곳에
쓰는 것이 아니다.** 여기서는 `tab.url` 이 없다는 사실 자체가 진단에 필요한
정보였는데 문법이 그것을 삼켰다. §13 의 "확인을 먼저 하는 습관이 기능을
껐다" 와 같은 계열이다. 방어가 기본값이 되면 무엇을 방어하는지 잊는다.

그리고 **조용히 되돌아가는 분기는 로그를 남긴다.** 이 코드에는 무음 return
이 셋 있었고 셋 다 정상 경로처럼 보였다. 어느 것이 발동했는지 알 방법이
없으면 남은 수단은 추측뿐이다.

세 번째로 **특별대우 하나가 사실을 세 곳에 복제했다.** Udemy 를 다른 사이트와
같이 다루자 중복이 저절로 사라졌다. 예외를 유지하는 비용은 예외 그 자체가
아니라 예외를 아는 코드의 수다.

## §15. 순회마다 다시 만들어지는 객체에 카운터를 두면 세지 않는다

**2026-09-12**

### 증상

워커를 끈 채로 페이지를 열자 `ERR_CONNECTION_REFUSED` 가 끝없이 반복됐다.
§12 에서 재시도 상한 `MAX_RETRY` 를 넣은 뒤였다.

### 원인

카운터를 `u.retry` 에 뒀다. `u` 는 유닛 객체이고, 유닛은 순회마다 어댑터의
`collect` 가 새로 만든다. **다음 순회의 `u` 는 다른 객체이므로 카운터가 매번
0 에서 시작한다.** 상한이 영영 걸리지 않는다.

`Failed to fetch` 는 `TypeError` 라 상태 코드가 없다. 일시 실패로 분류되어
재시도 경로로 갔고, 그 경로의 상한이 동작하지 않았다.

### 조치

카운터를 `el.dataset.stRetry` 로 옮겼다. DOM 요소는 순회를 넘겨 산다.
그리고 연속 실패가 3회 쌓이면 순회 자체를 멈춘다 — 워커가 꺼져 있는 상태는
페이지를 새로 열기 전에는 풀리지 않는다.

### 배운 것

**§12 에서 "실패를 잊는 재시도는 폭주" 라고 적고, 재시도 횟수를 잊는 코드를
같은 커밋에 남겼다.** 원인을 정확히 진단하고도 해법의 절반만 구현한 것이다.

판단 기준이 하나 생겼다. **상태를 어디에 두는가를 먼저 묻는다**(§2 와 같은
질문이다). 이 프로젝트에서 어려웠던 것은 매번 로직이 아니라 이 질문이었다.
카운터의 수명이 세려는 대상의 수명보다 짧으면 그것은 카운터가 아니다.

## §16. 규약을 알고도 같은 범주를 못 알아봤다

**2026-09-12**

### 증상

MDN 에서 아이콘을 두 번 누르자 `client.js` 가 통째로 죽었다.

`Uncaught SyntaxError: Identifier 'WorkerError' has already been declared`

### 원인

`client.js` 최상위에 `class WorkerError` 를 선언했다. 콘텐츠 스크립트는
아이콘 클릭과 `onUpdated` 로 재주입되고, 재주입되면 파일 전체가 다시
평가된다. `class` 선언은 `const` 와 같은 규칙이라 재선언이 `SyntaxError` 다.

MASTER §9 에 "최상위 `const` 도 쓰지 않는다. 재선언은 `SyntaxError` 다" 가
이미 적혀 있었다. **규약을 알고도 `class` 가 그 범주라는 것을 연결하지
못했다.**

파일 하나가 죽으면 `ST.translate` 가 갱신되지 않는다. 다른 파일은 각자
가드가 있어 멀쩡하므로, 브로커는 정상으로 보이는데 클라이언트만 옛 코드인
상태가 된다.

### 조치

`globalThis.ST.WorkerError ??= class ...` 로 바꿨다. 그리고 주입 전에
`globalThis.ST.__running` 을 물어 이미 돌고 있으면 주입하지 않는다.

### 배운 것

**규약을 지키려면 그 규약이 무엇의 집합인지 알아야 한다.** "최상위 `const`
금지" 를 글자 그대로 읽으면 `class` 는 빠져나간다. 규약을 쓸 때는 사례가
아니라 범주로 쓴다 — 여기서는 "재선언이 오류인 모든 선언" 이었다.

그리고 **DECISIONS §9 가 말한 그대로다.** 규약을 문서에 적는 것만으로는
지켜지지 않는다. 이것은 도구가 잡을 수 있는 종류다 — 콘텐츠 스크립트의
최상위 `let` · `const` · `class` 선언을 금지하는 검사 하나면 된다.

## §17. 코드만 있고 실행된 적 없는 계층은 검증된 것이 아니다

**2026-09-12**

### 증상

README 와 MASTER 가 "Layer 0 이 항상 참이므로 어댑터가 없는 사이트에서도
번역이 동작한다" 고 단언했다. `generic` · `standard` 어댑터는 코드만 있고
Udemy 외 사이트에서 한 번도 실행된 적이 없었다.

### 원인

Udemy 어댑터가 잘 도는 것을 보고 하위 계층도 같은 구조이므로 돌 것이라고
추정했다. 실제로 돌려 보니 주장이 성립하기 전에 여섯 가지가 막고 있었다.

- 권한 없는 탭의 `tab.url` 이 `undefined` 라 권한 요청까지 가지 못했다(§14)
- 상위 계층이 배타 선택에서 하위 계층을 덮어 본문이 빠졌다(§11)
- 실패한 유닛을 잊고 1.5초마다 재요청했다(§12)
- 재시도 카운터를 순회마다 새로 만들어지는 객체에 뒀다(§15)
- 콘텐츠 스크립트 재주입이 최상위 선언에서 죽었다(§16)
- 대상 언어와 같은 문자로 쓰인 텍스트까지 번역했다

### 조치

MDN(`generic`) 과 구글 폼(`standard`) 에서 검증했다. MDN 은 20개 유닛이
모두 붙고 실패 0 이며 순회가 멎는다. 구글 폼은 보기와 안내문이 함께
잡힌다. 위 여섯 결함을 모두 고쳤고 각각 별도 절로 남겼다.

### 배운 것

**"같은 구조이므로 동작할 것" 은 검증이 아니라 추정이다.** 여섯 개가 막고
있었고, 그중 어느 하나도 코드를 읽어서는 보이지 않았다. 전부 실제 브라우저
에서만 드러나는 종류였다.

그리고 **검증되지 않은 주장을 README 에 단정형으로 적지 않는다.** 이 저장소는
"어댑터 없이도 동작한다" 를 차별점으로 내세우면서 그것을 한 번도 확인하지
않은 상태로 문서에 적어 두었다. PLAN §2-1 이 ⚠ 로 표시해 둔 것이 유일한
방어선이었고, 그 표시가 없었으면 공개 시점에 거짓말이 될 뻔했다.

## §18. 해결됐다는 표시도 중복이다

**2026-09-12**

### 증상

PLAN 에서 #7 을 해결 처리하면서 `⬛` 로 바꾸고 그 아래에 검증 내용을 적었다.
사람이 지적해서야 고쳤다. §9 에서 같은 규약을 두 번 어겼다고 기록한 뒤에
세 번째로 어긴 것이다.

### 원인

규약 자체가 어기기 쉬웠다. `⬛` 는 "내용은 옮기고 포인터만 남긴다" 는 뜻인데,
포인터를 남길 자리가 있으면 거기에 무엇을 얼마나 쓸지 매번 판단해야 한다.
판단이 필요한 규약은 문맥이 끊기는 작업에서 지켜지지 않는다(§9).

그리고 포인터 자체가 이미 중복이었다. `| 7 | ⬛ | → DECISIONS §17 |` 이
알려주는 것은 DECISIONS §17 을 읽으면 전부 나온다. **미해결만 담는 문서에
해결된 행이 쌓이는 구조**였고, 시간이 지나면 PLAN 의 절반이 묘비가 된다.

### 조치

`⬛` 를 없앴다. 해결된 항목은 행째로 지운다. 번호는 재사용하지 않으므로
커밋과 DECISIONS 의 인용은 깨지지 않는다.

`doctor.sh` 의 검사도 뒤집었다. 전에는 "⬛ 행이 내용을 들고 있는가" 를 봤고
지금은 "⬛ 가 있는가" 만 본다. 판단이 없는 검사다.

### 배운 것

**"행 번호가 자산" 과 "행을 지우지 않는다" 를 같은 것으로 봤다.** 번호를
재사용하지 않으면 행은 지워도 된다. 요구사항을 구현과 붙여서 기억하면
구현을 바꿀 수 없게 된다.

그리고 **판단이 필요한 규약은 도구로 강제할 수 없고, 강제할 수 없는 규약은
지켜지지 않는다.** §9 에서 도구를 두고도 이 항목만 계속 새어 나간 이유가
그것이다. "포인터만 남긴다" 는 검사하기 어렵고 "없어야 한다" 는 한 줄이면
된다. **규약을 고칠 때 사람의 주의력이 아니라 검사 가능성을 기준으로 삼는다.**

## §19. 기준선을 모르고 정한 임계값은 검사가 아니다

**2026-09-13**

### 증상

골든셋의 길이 비율 검사가 원문의 1.91배를 출력한 항목을 통과시켰다. 그
항목은 번역을 마친 뒤 원문에 없는 문장을 하나 더 덧붙인, 명백한 환각이었다.

### 원인

임계값을 `ratio_max = 2.0` 으로 두었다. "출력이 원문의 2배를 넘으면 환각
신호" 라는 초기 판단을 그대로 옮긴 값이고, 그럴듯해 보였으므로 아무도
의심하지 않았다.

실측 분포를 보니 영한 번역의 정상 비율은 **0.44~0.53** 으로 매우 좁았다.
18유닛 중 16개가 그 띠 안에 있었다. 한국어가 영어보다 짧다는 사실을 알면서도
임계값에 반영하지 않았고, 그래서 **정상의 네 배가 되는 값을 상한으로 두고
있었다.** 그 아래로는 무엇이든 통과한다.

동시에 하한이 없어 요약도 잡히지 않았다.

### 조치

실측 상한 0.53 에 여유를 얹어 `ratio_max = 0.75`, 하한은 `ratio_min = 0.30`
으로 다시 잡았다. 이상치 둘이 새로 잡혔고 정상 16개는 그대로 통과했다.

### 배운 것

**골든셋이 자기 자신의 임계값을 교정했다.** 검사를 만들 때는 그 검사가 옳은지
확인할 방법이 없었고, 실제 분포를 보고서야 네 배 헐겁다는 것을 알았다.
측정 도구를 만들면 먼저 그 도구로 기준선을 뽑고, 임계값은 그다음에 정한다.

그리고 **DECISIONS §6 과 같은 계열이되 대상이 다르다.** §6 에서는 측정값이
실사용을 대표하지 않았고, 여기서는 판정 기준이 실사용을 대표하지 않았다.
둘 다 "실제로 재 보기 전에는 모른다" 는 같은 말이다.

세 번째로 **같은 결함을 두 각도에서 잡는 검사가 낫다.** 물음표 소실로 잡히던
항목이 길이 비율로도 잡혔다. 물음표는 의문문에서만 쓸 수 있지만 길이는 모든
유닛에 적용되므로, 후자가 더 일반적인 검출기다.

## §20. 프롬프트에서 지시의 위치가 효과를 정한다

**2026-09-13**

### 증상

항목별 호출을 한 프롬프트 배치로 묶자 환각이 사라졌다. 길이 이상 2건과
물음표 소실 1건이 0 이 되었다. 그런데 용어집 위반이 2 → 4, 문체 위반이
1 → 3 으로 늘어 총 위반은 6 → 8 이 되었다.

### 원인

배치 규칙을 `system + BATCH_RULE` 로 이어 붙였다. 용어집 지시가 시스템
프롬프트 중간에 놓이고 그 뒤에 배치 규칙이 왔다. 프롬프트가 길어지자 중간에
놓인 용어집이 묻혔다.

출력을 보면 일관성 자체는 생겼다. 같은 용어가 모든 조각에서 같은 표기를
썼다. 다만 **용어집이 아니라 모델이 고른 표기로 통일됐다.** 배치가 일관성을
만들어 준 것은 맞고, 어느 쪽으로 통일할지를 지시하지 못한 것이 문제였다.

### 조치

배치 경로의 프롬프트를 `SYSTEM + BATCH_RULE + 용어집` 으로 재배치했다.
용어집을 맨 뒤에 둔다. 위반 8 → 5 로, 개별 호출(6)보다도 낮아졌다.

### 배운 것

**트레이드오프처럼 보이는 것이 버그일 수 있다.** 처음 결과만 보면 배치가
환각과 일관성을 맞바꾼 것으로 읽힌다. 실제로는 지시 하나가 묻힌 것이었고,
순서를 바꾸자 양쪽을 다 얻었다. 무엇을 포기할지 정하기 전에 정말 포기해야
하는지 먼저 확인한다.

그리고 **프롬프트를 문자열 연결로 조립하면 순서가 암묵적으로 정해진다.**
`system + BATCH_RULE` 은 자연스러워 보이지만 용어집을 중간으로 밀어 넣는다.
경로마다 필요한 지시가 다르므로 경로마다 조립한다.

세 번째로 **골든셋이 없었다면 배치를 되돌렸을 것이다.** 위반 8 은 개별 호출
6 보다 나쁘고, 그 숫자만 보면 배치가 실패한 것으로 보인다. 숫자를 종류별로
쪼개 보아야 환각 3 건이 사라진 것과 문체 2 건이 는 것이 보인다. **총합은
판단 근거가 되지 못한다.**

## §21. 새로 만든 검사는 먼저 기존 자산에 돌린다

**2026-09-13**

### 증상

하루 사이에 네 번, 검사가 위반을 보고했는데 실제로는 검사가 틀렸다.

| 검사 | 무엇이 틀렸나 |
|---|---|
| 용어집 위반 | 포함 관계·고유명사를 구분하지 못했다 |
| 길이 비율 | 임계값이 정상의 네 배였다(§19) |
| 합니다체 | 의문형 종결어미를 빠뜨렸다 |
| PLAN 전건 | 정규식에 MULTILINE 이 없어 매치가 거의 없었다 |

마지막 것은 실재하는 전건 22건을 한꺼번에 "존재하지 않는다" 로 보고했다.

### 원인

넷 다 같은 자리에서 났다. **검사를 쓰고 나서 그 검사가 옳은지 확인하지
않았다.** 코드가 그럴듯해 보였고 통과할 것이라고 가정했다.

PLAN 전건 검사는 같은 정규식을 `finditer` 와 `match` 두 방식으로 썼는데
한쪽만 깨졌다. `^` 는 MULTILINE 없이 문자열 전체의 시작만 가리킨다. 줄 단위
`match` 는 정상이었으므로 코드를 읽어서는 보이지 않았다.

### 조치

새 검사를 켤 때 **먼저 기존 문서 전체에 돌린다.** 통과하면 검사가 옳거나
자산이 깨끗하고, 대량으로 실패하면 십중팔구 검사가 틀렸다. 22건이 한꺼번에
나온 것이 그 신호였다.

`check_docs.py` 가 위반은 1, 도구 고장은 2 로 끝나게 했다. `doctor.sh` 는
둘을 다르게 보고한다.

### 배운 것

**검사도 코드이고 코드에는 결함이 있다.** 검사가 무엇을 잡는지만 보고
무엇을 놓치는지는 보지 않았다. 일부러 위반을 만들어 잡히는지 확인하는 것이
검사를 검사하는 유일한 방법이다.

그리고 **조용히 아무것도 하지 않는 검사가 가장 위험하다.** 오늘 넷은 전부
요란하게 틀려서 잡혔다. 만약 `nums` 가 비는 대신 모든 번호를 담았다면
검사는 언제나 통과했을 것이고, 아무도 그것이 죽었다는 것을 몰랐을 것이다.
**통과는 검사가 작동한다는 증거가 아니다.**

세 번째로 **위반과 고장을 같은 출구로 내보내지 않는다.** 둘을 구분하지
않으면 도구가 깨진 것을 자산이 틀린 것으로 읽는다.

## §22. 검사 대상을 뭉뚱그리면 맞는 코드를 위반으로 잡는다

**2026-09-13**

### 증상

콘텐츠 스크립트의 최상위 선언을 금지하는 검사를 켜자 `background.js` 의
`const` 두 건이 위반으로 잡혔다. 그 둘은 올바른 코드다.

### 원인

검사 대상을 `extension/src/*.js` 로 적었다. 그 글롭에는 서비스 워커인
`background.js` 가 포함된다. 서비스 워커는 한 번만 평가되고 재주입되지
않으므로 최상위 `const` 가 문제되지 않는다. §16 의 결함은 주입되는 파일에만
해당한다.

**규칙은 옳았고 적용 범위가 틀렸다.**

### 조치

주입 파일 목록을 `background.js` 의 `ST_FILES` 에서 읽어 그 파일들만 본다.
파일이 늘어도 검사가 따라가고, 목록을 두 곳에 적는 실수(§14)도 피한다.

검사를 고친 뒤 일부러 위반을 넣어 잡히는지 확인했다. 줄 번호까지 정확히
보고했고, 빼니 다시 통과했다.

### 배운 것

**"어디에 적용되는가" 는 "무엇을 금지하는가" 만큼 중요하다.** 규칙을 옮겨
적을 때 근거가 된 상황의 조건도 함께 옮겨야 한다. 여기서는 "재주입된다" 가
그 조건이었고, 글롭을 쓰는 순간 그 조건이 사라졌다.

그리고 **검사 대상 목록을 손으로 적지 않는다.** 코드가 이미 들고 있는 목록을
읽으면 두 곳이 어긋날 일이 없다.

## §23. 덮어쓰는 중복 정의는 아무것도 깨뜨리지 않아 조용하다

**2026-09-13**

### 증상

`engine.py` 에 배치 관련 정의가 통째로 두 번 들어 있었다. `BATCH_MARK` ·
`_MARK_RE` · `BATCH_RULE` · `_join` · `_split` 이 47 줄에 걸쳐 그대로 반복됐고
`log = logging.getLogger("thoth")` 도 두 번 있었다. 테스트 42 건이 전부
통과하는 상태였다.

### 원인

파이썬의 최상위 재정의는 오류가 아니라 덮어쓰기다. 뒤 정의가 앞을 가리므로
동작은 한 벌만 있을 때와 완전히 같다. 자동 검사 중 어느 것도 이것을 보지
않았다 — 테스트는 동작을 보고, `check_docs.py` 는 문서를 보고, `doctor.sh` 의
확장 검사는 JS 만 본다.

**결함이 아니라 함정이었다.** `_split` 을 고칠 때 위쪽을 고치면 아무 일도
일어나지 않고, 아래쪽을 고치면 동작이 바뀐다. 어느 쪽을 고쳤는지 모르는
상태에서 실측을 하면 그 실측이 무엇을 잰 것인지도 모른다.

### 조치

뒤 블록과 중복 `log` 선언을 지웠다. 테스트 수와 결과가 그대로였다 — 그것이
이 항목이 테스트로 잡히지 않는다는 증거다.

### 배운 것

**조용한 중복은 조용한 결함보다 늦게 발견된다.** 깨지는 중복은 즉시 잡히지만
덮어쓰는 중복은 영원히 통과한다. §21 이 "통과는 검사가 작동한다는 증거가
아니다" 라고 적었고 여기서는 한 겹 더 나아간다 — **통과는 코드가 한 벌이라는
증거도 아니다.**

그리고 **사람이 읽어서 잡는 것에는 상한이 있다.** 이 파일은 여러 세션에 걸쳐
수정됐고(§9) 그때마다 사람이 읽었다. 같은 블록이 두 번 있는 것을 아무도
알아채지 못했다. 코드 중복은 문서 중복과 달리 강제자가 없었다.

## §24. 요청 전체를 실패시키면 이미 가진 것까지 버린다

**2026-09-13**

### 증상

월 상한에 걸린 사용자가 **이미 번역되어 캐시에 있는 문장조차 보지 못했다.**
`/translate` 가 가드 실패에서 429 하나로 끝났고, 같은 요청에 섞여 있던 캐시
히트는 응답에 실리지 않았다.

### 원인

가드를 "요청을 통과시킬 것인가" 로 설계했다. 실제로 가드가 지키는 것은
**번역 호출**이지 요청이 아니다. 캐시 히트는 호출을 만들지 않으므로 과금이
0 이고, 상한과 아무 관계가 없다. 관계없는 것을 같은 판정에 묶었다.

413(길이 초과)과 503(카운터 불통)도 같은 자리를 탔다. 셋 다 한 요청 안의
일부만 막으면 되는 사유인데 전부를 막았다.

### 조치

가드 실패에서 히트가 하나라도 있으면 200 으로 내린다. 못 채운 자리는 `null`
이고 `partial` 에 사유를 싣는다. 히트가 없으면 종전대로 상태 코드로 끝난다 —
돌려줄 것이 없는데 200 을 쓸 이유가 없다.

**엔진 실패(502)는 일부러 이 규칙에서 뺐다.** 방향이 반대이기 때문이다.
가드 실패는 재시도로 풀리지 않으므로 그 자리를 버리는 것이 맞고, 엔진 실패는
일시적이라 재시도가 맞다. 200 으로 내리면 확장이 재시도할 근거를 잃고 그
자리를 영구 실패로 버린다(§12).

부분 응답은 200 이지만 사유는 영구적이므로, 브로커가 `partial` 을 받으면
순회를 멈춘다. 멈추지 않으면 캐시 히트만 계속 받으면서 1.5 초마다 워커를
때린다.

`bench_golden.py` 도 `partial` 에서 멈추게 했다. 캐시 히트만으로 잰 처리율은
엔진의 값이 아니고, 그 수치가 `baseline.json` 에 들어가면 기준선이 조용히
오염된다(§19).

### 배운 것

**"막는다" 의 단위를 요청이 아니라 비용이 드는 행위에 맞춘다.** 요청은
사용자가 묶은 것이고 과금은 그 묶음과 무관하다. 가드가 요청을 보면 관계없는
항목이 같이 죽는다.

그리고 **같은 실패도 재시도 가능성이 다르면 다른 형태로 알려야 한다.** 상태
코드 하나로 뭉뚱그리면 호출자가 다음 행동을 고를 수 없다. 여기서 가드 실패와
엔진 실패를 갈랐고, 그 경계는 §12 가 4xx · 5xx 로 그은 경계와 같다.

## §25. 상한은 비용을 막지 남용을 막지 않는다

**2026-09-13**

### 증상

워커에 인증이 전혀 없었다. `POST /translate` 는 어떤 자격도 요구하지 않고,
CORS 는 `allow_origins=["*"]` 다. 로컬 개발에서는 문제가 아니지만 배포 계획은
Lambda Function URL 이다(PLAN §2-3 #17). **URL 만 알면 누구나 번역기를 쓴다.**

### 원인

비용 가드를 만들면서 "상한이 있으니 최악이 한정된다" 로 정리하고 넘어갔다.
한정되는 것은 **지출**이고 한정되지 않는 것은 **누가 그 상한을 쓰는가** 다.
남이 200 만 자를 태우면 그달의 정당한 사용자가 429 를 받는다. 지출은 0 원
늘지 않았는데 제품은 죽는다.

PLAN §6 위험표에 이 항목이 없었다. 비용 · DOM 변경 · 크레딧 만료는 적혀
있었고 노출만 빠졌다. **적어 둔 위험의 목록이 곧 생각해 본 위험의 목록이라고
믿은 것**이 원인이다.

### 조치

`WORKER_TOKEN` 을 넣었다. 비면 열리고(로컬 기본값) 채우면 `X-Thoth-Token`
헤더를 `secrets.compare_digest` 로 대조한다. 문자열 `==` 는 앞에서부터 끊어
길이와 접두사가 새어 나간다.

401 도 `_err` 를 타므로 CORS 헤더가 붙는다. 인증 실패가 브라우저 콘솔에 CORS
위반으로 보이면 원인을 찾지 못한다(§2).

`/health` 는 토큰 없이도 답하되 잔여 문자를 싣지 않는다. 기동 여부는 누구나
물을 수 있어야 하고 — 헬스체크가 비밀을 들고 다니면 안 된다 — 남의 상한이
얼마나 닳았는지는 공개할 정보가 아니다.

`doctor.sh` 가 원격 설정(`ENGINE=bedrock|translate` 또는 `CACHE=ddb`)에서
토큰이 비면 FAIL 한다. 로컬 설정에서는 OK 로 가른다. 뭉뚱그리면 맞는 상태를
위반으로 잡는다(§22).

### 배운 것

**확장에 심는 토큰은 비밀이 아니다.** 사용자가 꺼내볼 수 있으므로 이것은
작정한 공격자를 막지 못한다. 막는 것은 "엔드포인트를 주운 사람" 이고, 그것이
실제 위험의 대부분이다. **완전하지 않다는 이유로 아무것도 두지 않는 것이
가장 나쁜 선택**이다.

그리고 **가드를 만들면 그 가드가 막는 것의 경계를 적어 둔다.** "월 상한이
있다" 는 문장은 "남용이 막힌다" 로 쉽게 읽힌다. 무엇을 막는지만 적고 무엇을
막지 않는지 적지 않으면 그 공백이 안전으로 오해된다.

## §26. 줄끝이 바뀐 패치는 내용이 틀린 것처럼 보인다

**2026-09-13**

### 증상

윈도우 다운로드 폴더로 받은 패치를 `git apply` 하자 모든 파일에서
`patch does not apply` 가 났다. 패치는 방금 만든 것이고 저장소는 그 패치를
만든 시점과 같은 상태였다.

### 원인

브라우저를 거치면서 줄끝이 CRLF 가 되었다. 저장소는 전부 LF 이므로 문맥 줄이
한 줄도 맞지 않는다. `git apply` 는 문맥 불일치를 보고 "패치가 안 맞는다" 고
말하는데, **그 말은 내용이 어긋났다는 뜻으로 읽힌다.** 실제로 어긋난 것은
보이지 않는 바이트 하나다.

오류가 모든 파일에서 한꺼번에 나는 것이 신호였다. 내용이 어긋나면 어긋난
파일에서만 나고, 전부에서 나면 파일별 사정이 아니라 공통 처리에 문제가 있다.

### 조치

`tools/apply_patch.sh` 를 만들었다. `.env` 의 `WIN_DOWNLOADS` 를 읽어 가장
최근 패치를 고르고, 사본을 `/tmp` 에 두어 줄끝을 벗긴 뒤 적용한다. 원본은
건드리지 않으므로 실패해도 다시 받을 필요가 없다.

같은 패치를 두 번 돌리는 경우를 가르게 했다. 역적용(`git apply --check -R`)이
되면 이미 붙은 패치다. 검증 중에 이것이 "붙지 않는다" 로만 보고되는 것을
발견했는데, 이미 적용된 상태와 저장소가 어긋난 상태는 **대응이 정반대**다.
전자는 아무것도 하지 않는 것이 맞고 후자는 저장소를 봐야 한다.

적용 뒤 `.env` 와 `.env.example` 의 키를 비교해 보고한다. 패치는 `.env` 를
담지 못하므로 키가 늘어난 것을 사람이 알 방법이 이것뿐이다.

### 배운 것

**오류 메시지는 증상을 말하지 원인을 말하지 않는다.** "패치가 안 맞는다" 는
정확한 관찰이고 완전히 오해를 부르는 문장이다. 도구가 가리키는 층위와 실제
원인의 층위가 다를 때, 메시지를 그대로 믿으면 엉뚱한 곳을 판다.

그리고 **전송 경로가 내용을 바꾼다.** 저장소 안에서만 생각하면 LF 로 통일된
세계지만 파일이 브라우저와 DrvFs 를 거치는 순간 그 전제가 깨진다. 경계를
넘는 지점마다 무엇이 바뀌는지 적어 둔다 — §3 이 DrvFs 의 속도를, 여기서는
줄끝을 잡았고 둘 다 같은 경계에 있다.

세 번째로 **검증이 실패해야 검증이다.** 스크립트를 만들고 정상 경로만 돌려
봤으면 재적용 판별이 빠진 것을 몰랐다. 일부러 같은 패치를 두 번 돌린 것이
그것을 드러냈다(§21).

## §27. 측정 구간에 번역이 아닌 것이 들어 있었다

**2026-09-13**

### 증상

기준선을 재현하려고 골든셋을 다시 돌렸다. 위반은 4 건으로 종류까지 똑같이
나왔는데 **처리율만 30자/초에서 23자/초로 어긋났다.** 코드도 골든셋도 모델도
같았다.

### 원인

배치별 시간에 답이 있었다. 같은 9유닛인데 첫 배치가 156.6s, 둘째가 79.8s 로
두 배 갈렸다. 차이 76.8초는 번역이 아니라 **모델 로딩**이다.

기준선을 잴 때는 ollama 가 이미 올라와 있었고 재현할 때는 콜드였다. 러너는
그 차이를 모른다. **재는 사람이 직전에 무엇을 했는지가 수치를 정하고 있었다.**

`docs/bench/README.md` 는 캐시를 비우라고만 적었다. 비워야 할 상태가 캐시
말고도 있다는 것을 몰랐고, §6 에서 캐시 히트가 속도를 거짓으로 만든다는 것을
배우고도 **같은 범주의 다음 항목을 찾지 않았다**(§16 과 같은 실패다).

이것이 지금 문제인 이유는 #12 다. 호스팅 엔진에는 모델 로딩이라는 개념이
없다. 웜업 없이 재면 로컬이 존재하지 않는 페널티를 지고 들어가고, "호스팅이
N배 빠르다" 는 결론이 그 오염 위에 선다. **엔진을 고르려고 만든 기준선이
엔진 선택을 왜곡한다.**

### 조치

`bench_golden.py` 가 본 측정 전에 짧은 문장 하나를 태운다. 그 시간은 집계에서
빼되 버리지 않고 따로 보고한다 — 로딩 비용은 그 자체로 알 만한 값이고, 0 에
가까우면 이미 웜이었다는 뜻이다.

**웜업 문장에 매번 다른 nonce 를 넣는다.** 고정 문장이면 두 번째 실행부터
캐시 히트라 모델을 태우지 않는다. 웜업이 조용히 아무것도 하지 않게 되고,
통과는 그것을 알려주지 않는다(§21). 테스트로 이것을 고정했고, 일부러 고정
문장으로 되돌려 잡히는지 확인했다.

골든셋 문장을 웜업에 쓰지 않는다. 쓰면 그 문장이 캐시에 올라가 본 측정이
히트가 되고, 캐시를 비우고 재는 규약이 웜업 때문에 무효가 된다.

`--no-warmup` 을 남겼다. 콜드 로딩 비용 자체를 재려는 경우다. 그 값은
기준선에 넣지 않는다.

PLAN 의 실측 요약이 "위반 5 · 문체 2 · 용어 2 · 고유명사 2" 로 남아 있었다.
총계와 내역의 합이 어긋나고 기준선의 4 와도 달랐다. 검사를 고치기 전 숫자가
한쪽에만 남은 것이다. 기준선 값으로 맞췄다.

### 배운 것

**"같은 조건" 은 적어 두지 않으면 같지 않다.** 캐시는 비우라고 적혀 있어서
비웠고 모델 상태는 적혀 있지 않아서 아무도 보지 않았다. 재현 절차에서 빠진
조건은 조건이 아니라 우연이 된다.

그리고 **한 번 배운 범주는 끝까지 훑는다.** §6 이 "측정 구간에 번역이 아닌
것이 섞이면 안 된다" 를 캐시에서 배웠다. 같은 문장이 모델 로딩에도 그대로
적용되는데 그때 찾지 않았다. 교훈을 사례에 묶어 두면 다음 사례에서 다시
배운다.

세 번째로 **재현은 값이 맞는지 보는 일이 아니라 절차가 완전한지 보는 일이다.**
위반 4 가 그대로 나온 것에 안심하고 넘어갔으면 속도 항목은 영원히 흔들리는
채로 남았을 것이다. 두 수치 중 하나만 재현된 것이 절차에 구멍이 있다는 신호였다.

## §28. 같은 질문에 두 곳이 다르게 답하고 있었다

**2026-09-13**

### 증상

45유닛 실측에서 `q5-p` 가 `throughput` 용어 위반으로 잡혔다. 그런데 그 지문에
`throughput` 은 단독으로 나오지 않는다. 원문에 없는 용어의 한국어 표기를
검사가 요구한 것이다.

### 원인

`bench_golden.check` 가 "이 용어가 원문에 있는가" 를 `t in low` 로 물었다.
부분 문자열 포함이므로 `ProvisionedThroughputExceededException` 안의
`throughput` 이 걸린다.

같은 질문을 `glossary._hits` 는 `\b{term}(s|es|ing|ed)?\b` 로 묻는다. **두 곳이
같은 판단을 서로 다른 규칙으로 하고 있었고, 한쪽이 틀렸다.** 검사 쪽이 더
느슨해서 오탐을 냈다.

단순히 단어 경계 `\b{term}\b` 로 좁히면 이번에는 `records` 가 `record` 에 걸리지
않는다. 케이스 전수로 재 보니 그 변경은 20건 중 19건을 함께 떨어뜨렸다 —
복수형이 대부분이고, 그것들은 **걸려야 맞는** 것이다. 검사를 고치려다 조용히
약하게 만들 뻔했다(§21).

### 조치

`glossary._hits` 와 같은 굴절 패턴으로 맞췄다. 케이스 전수에서 빠지는 것이
정확히 1건인지 먼저 확인하고 바꿨다. 부분 문자열로 되돌렸을 때와 단어 경계만
걸었을 때, 양쪽에서 각각 다른 테스트가 실패하는 것도 확인했다.

### 배운 것

**같은 판단을 두 곳에서 하면 언젠가 갈린다.** §14 는 같은 사실이 세 곳에 다른
문법으로 살던 문제였고 여기서는 같은 질문에 두 개의 답이 있었다. 후자가 더
찾기 어렵다 — 값이 아니라 규칙이 중복이라 눈에 띄지 않는다.

그리고 **검사를 좁힐 때는 무엇이 함께 빠지는지 먼저 센다.** 오탐 하나를 보고
조건을 좁히면 정탐까지 같이 사라진다. 고치기 전에 전수로 차이를 내 보는
한 번의 계산이 그것을 막는다.

## §29. 코드가 미래 문서를 인용하면 그 항목이 해결될 때 깨진다

**2026-09-13**

### 증상

`#14` 를 지우려다 그 번호를 가리키는 곳이 아홉 군데인 것을 발견했다. 그중
셋이 코드 주석이었다. 그리고 **`#13` 은 이미 깨져 있었다** — 앞선 작업에서
지우고 `#45` 로 다시 세웠는데 `broker.js` 와 `udemy.js` 가 옛 번호를 가리킨
채였다. `bench_engine.sh` 는 `#37` 의 절 번호가 틀려 있었다.

### 원인

PLAN 은 미해결만 담고 해결된 항목은 행째로 지우며 번호를 재사용하지 않는다
(§18). 그 세 규칙이 함께 있으면 **PLAN 번호를 인용한 코드는 그 항목이 해결되는
순간 영영 빈 곳을 가리킨다.** 해결은 좋은 일이므로 이 파손은 반드시 온다.

`check_docs.check_plan` 은 PLAN **안**의 전건만 본다. 바깥에서 들어오는 참조는
아무도 보지 않았고, 그래서 `#13` 이 깨진 것을 사람이 `#14` 를 지우다가 우연히
알았다.

근거의 성질도 잘못 짚었다. 후처리가 왜 있는지는 **이미 일어난 일**이므로
DECISIONS 가, 지금 무엇을 하는지는 MASTER 가 담는다. 코드가 PLAN 을 가리킨
것은 "이 결함이 아직 남아 있다" 는 뜻이었는데, 결함이 사라져도 코드는 남는다.

### 조치

코드와 부속 문서의 PLAN 항목 참조를 정리했다. 후처리의 근거는 DECISIONS §20 과
MASTER §7-2 로 옮겼고, 살아 있는 항목을 가리키던 것은 새 번호로 고쳤다.

`check_docs.check_refs` 를 추가했다. 저장소의 코드와 문서에서 `PLAN §N #M` 을
모아 그 번호가 PLAN 에 실재하는지 본다. **절 참조(`PLAN §4`)는 검사하지
않는다** — 절은 주제로 나뉘어 안정적이고 사라지는 것은 항목뿐이다. 대상을
뭉뚱그리면 맞는 것을 위반으로 잡는다(§22).

§21 대로 먼저 기존 자산 전체에 돌렸다. 통과했고, 그다음 없는 번호 · 지운
번호 · 절 참조 세 가지로 일부러 깨뜨려 앞의 둘만 잡히는 것을 확인했다.

### 배운 것

**문서의 시제가 인용의 수명을 정한다.** 과거를 담는 문서는 고쳐지지 않으므로
영원히 인용할 수 있고, 미래를 담는 문서는 비워지는 것이 목적이므로 인용하면
안 된다. 어느 문서를 가리킬지는 취향이 아니라 그 문서가 무엇을 담기로 했는지가
정한다.

그리고 **규약이 스스로 만드는 파손은 규약과 함께 검사를 붙인다.** "지운다" 와
"재사용하지 않는다" 를 정한 시점에 이 파손은 이미 예정되어 있었다. 그때
검사도 같이 만들었어야 했다.

## §30. 같은 종류의 지시가 두 메커니즘에 나뉘어 있었다

**2026-09-13**

### 증상

45유닛 실측에서 고유명사 위반 3건이 전부 같은 모양이었다. `Data Catalog` 가
"데이터 카탈로그", `DynamoDB Streams` 가 "DynamoDB 스트림" 으로 나왔다.
**복합 고유명사의 뒷부분만 한글이 된다.**

### 원인

`keep` 토큰 14건을 전수 대조했다. 깨진 것은 **뒷말이 용어집 등재어이고 동시에
규칙 1 의 `e.g.` 목록에 없는 것**뿐이었고 반례가 없었다.

`Kinesis Data Streams` 는 뒷말이 등재어(`stream`)인데도 살아남았다 — 예시에
적혀 있다. `Redshift Spectrum` 은 예시에 없는데도 살아남았다 — 뒷말이 등재어가
아니다. 두 조건이 함께 참일 때만 깨진다.

즉 **모델이 규칙 1 을 일반화하지 않고 예시를 목록으로 취급한다.** 목록에 없는
이름을 만나면 더 구체적인 지시인 용어집으로 넘어간다.

더 깊은 원인은 구조다. 규칙 1 과 용어집은 **같은 종류의 지시**다 — 둘 다 "이
용어는 이렇게 써라" 를 말한다. 그런데 한쪽은 프롬프트의 예시로, 다른 한쪽은
데이터로 있었다. 나뉘어 있으니 부딪쳤고, 부딪치면 데이터가 이겼다.

### 조치

용어집에 **항등 항목**을 넣었다. 표기가 en 과 같으면 "번역하지 말라" 는 뜻이다.
AWS Custom Terminology 에 `Data Catalog -> Data Catalog` 를 등재하는 것과 같은
발상이고, 이 저장소는 그 방식을 이미 프롬프트 기반으로 채택해 두었다. 빠져
있던 것은 항등 매핑 하나였다.

`as_prompt` 가 항등 항목을 번역 목록과 줄을 나눠 싣는다.
`Data Catalog -> Data Catalog` 는 사람에게는 자명하나 모델에게는 번역 지시
형식 그대로라, 나머지와 같은 자리에 놓이면 무엇을 하라는 것인지 흐려진다(§20).

**예시를 늘리는 쪽은 택하지 않았다.** 이름이 늘 때마다 예시가 자라야 하고,
그것은 §8 이 커버리지 경쟁이라며 거부한 구조다. 항등 항목은 원문에 실제로
나타난 것만 배치마다 실리므로 등재가 늘어도 프롬프트가 자라지 않는다.

등재 기준은 그대로 두었다 — 이미 깨진 두 이름만 넣었고 `Kinesis Data Streams`
는 넣지 않았다.

### 배운 것

**같은 종류의 지시는 한 메커니즘에 모은다.** §14 는 같은 사실이 세 곳에 다른
문법으로 살던 문제였고 §28 은 같은 질문에 두 답이 있던 문제였다. 여기는 같은
지시가 두 전달 경로로 나뉜 경우다. 셋 다 "하나로 모았어야 했다" 로 끝난다.

그리고 **예시는 규칙이 아니다.** `e.g.` 를 붙이면 사람은 규칙의 사례로 읽고
모델은 허용 목록으로 읽는다. 규칙으로 일반화되기를 기대한 것이 잘못이었다.

세 번째로 **전수 대조가 가설을 만든다.** 위반 3건만 보면 "용어집과 규칙 1 이
충돌한다" 까지가 한계다. 깨지지 않은 11건을 함께 놓아야 예시 여부라는 두 번째
축이 보인다. **틀린 것만 보면 원인을 반만 본다.**

## §31. 사람이 표시해야 도는 검사는 표시하지 않은 날 죽는다

**2026-09-13**

### 증상

기준선이 늙었는지를 `stale` 플래그로 표시하게 했다. 검사를 시험해 보니 플래그를
**세우지 않은 경우**는 아무것도 잡히지 않았다. 프롬프트를 고치고 기준선을
그대로 둔 채 커밋해도 전부 통과한다.

### 원인

`stale` 의 정의도 좁았다. 처음에는 "골든셋 규모가 달라진 경우" 로 두었는데,
프롬프트나 용어집이 바뀌어도 위반 수는 그대로 무효가 된다. **규모가 같아도 값이
늙는다.**

더 큰 문제는 검사가 사람의 성실성 위에 서 있던 것이다. 플래그를 세우는 것도
사람, 지우는 것도 사람이니 잊으면 검사가 조용해진다. §21 이 "통과는 검사가
작동한다는 증거가 아니다" 라고 적은 자리로 다시 돌아왔다.

### 조치

번역 결과를 정하는 입력 — `SYSTEM` · `BATCH_RULE` · 용어집 전체 — 을 해시해
기준선에 박았다. 러너가 매 실행마다 지문을 찍고, 기준선의 지문과 다른데
`stale` 이 아니면 테스트가 실패한다. **코드가 스스로 늙었다고 말한다.**

지문에는 **모델이 보는 것만** 넣는다. 후처리나 배치 파싱을 고쳐도 흔들리면
관계없는 재측정을 요구하게 된다(§22). 그 경계를 테스트로 고정했다 — 후처리
규칙과 배치 구분자를 바꿔도 지문이 같고, `SYSTEM` 에 한 줄을 더하면 달라진다.

`stale` 에는 사유를 필수로 두었다. 플래그만 있으면 왜 세웠는지 잊히고, 잊히면
지울 수 없어 영영 남는다. `doctor.sh` 가 stale 을 SKIP 으로 보고한다 — FAIL 이
아닌 이유는 코드를 고친 커밋과 재측정 커밋이 나뉠 수밖에 없기 때문이고,
조용히 지나가지 않는 이유는 그래야 플래그가 지워지기 때문이다.

### 배운 것

**사람이 세우는 플래그는 검사가 아니라 메모다.** 잊을 수 있는 것을 검사의
전제로 두면 잊은 날에만 정확히 실패한다. 기계가 스스로 알 수 있는 것이면
기계에게 시킨다.

그리고 **정의가 좁으면 검사는 좁게만 돈다.** `stale` 을 "규모 불일치" 로
정의한 순간, 규모가 같은 모든 늙음이 검사 밖으로 나갔다. 이름을 정할 때 그
이름이 무엇을 덮지 못하는지도 같이 적는다.

## §32. 모순을 남긴 프롬프트는 결과를 정하지 못한다

**2026-09-13**

### 증상

항등 항목을 넣고 다시 재니 고유명사 위반이 3 → 2 로만 줄었다. `DynamoDB
Streams` 는 살아났는데 `Data Catalog` 는 그대로 깨졌다. **같은 조치가 하나는
먹히고 하나는 안 먹혔다.**

### 원인

두 배치의 프롬프트를 뽑아 보니 둘 다 같은 모순을 안고 있었다.

```
  catalog -> 카탈로그          |   stream -> 스트림
  These are proper names:      |   These are proper names:
    Data Catalog               |     DynamoDB Streams
```

항등 항목을 넣으면서 **원래 있던 짧은 용어를 빼지 않았다.** 용어집이 한쪽에서
"카탈로그로 써라" 하고 다른 쪽에서 "Data Catalog 를 그대로 둬라" 한다. 모델은
둘 중 하나를 고르고, 무엇을 고를지는 프롬프트가 정하지 않는다.

무엇이 갈랐는지는 확인하지 않았다. 앞말이 브랜드(`DynamoDB`)냐 일반명사
(`Data`)냐로 보이지만, **그것을 알아낼 필요가 없다** — 모순을 없애면 고를
것이 하나뿐이다.

`check()` 는 이 일을 이미 하고 있었다. "긴 용어에 포함된 짧은 용어는 빼고
본다" 가 그 코드의 주석이다. **검사만 그렇게 하고 프롬프트는 그러지 않았다.**
§28 과 §30 에 이어 같은 질문에 두 답이 있는 세 번째 자리다.

### 조치

`as_prompt` 가 항등 항목 안에 들어 있는 짧은 용어를 번역 목록에서 뺀다.
굴절형까지 본다 — `DynamoDB Streams` 의 `stream` 을 놓치면 모순이 남는다(§28).

관계없는 용어는 그대로 남는다. 테스트로 양쪽을 고정했다.

### 배운 것

**갈린 결과는 조치가 부분적으로 먹혔다는 뜻이 아니라 결정되지 않았다는
뜻이다.** 절반의 성공을 보고 "무엇이 달랐나" 를 물으면 원인을 찾는 데로 가는데,
물어야 할 것은 "왜 결정되지 않았나" 였다. 전자는 조사고 후자는 설계다.

그리고 **같은 판단을 하는 곳을 찾을 때는 이미 고친 곳의 반대편을 본다.**
세 번 모두 한쪽은 검사, 다른 쪽은 실행 경로였다. 검사를 고칠 때 실행 경로도
같이 봤어야 했다.

---

## §33. 데이터만 해시하면 조립 로직의 변경을 놓친다

**2026-09-13**

### 증상

§31 에서 만든 프롬프트 지문이 `as_prompt` 의 변경을 잡지 못했다. 로직을 고쳐
프롬프트 출력이 실제로 달라졌는데 지문은 그대로였다.

### 원인

지문에 `SYSTEM` · `BATCH_RULE` · 용어집만 넣었다. 셋 다 값이다. **모델이 보는
것에는 값뿐 아니라 그 값을 어떻게 배치하는지도 들어간다.** 조립 로직은 코드에
있고 지문은 데이터만 봤다.

§31 이 "코드가 스스로 늙었다고 말한다" 고 적었는데, 말하지 않는 구멍이 남아
있었다. 검사를 만든 그 자리에서 검사의 범위를 잘못 잡은 것이다.

### 조치

고정 표본을 한 번 조립해 그 결과를 함께 해시한다. 로직이 바뀌면 출력이 바뀌고
지문이 흔들린다. 값이 아니라 형태를 보므로 무관한 수정에는 흔들리지 않는다.

`as_prompt` 에 한 줄을 덧붙여 지문이 실제로 달라지는지 테스트로 고정했다.

### 배운 것

**"무엇이 출력을 정하는가" 를 셀 때 코드를 빼먹기 쉽다.** 데이터는 눈에 보이고
목록으로 만들기 쉬운 반면, 그것을 다루는 코드는 배경처럼 취급된다. 재현성을
보장하려는 지문이라면 입력과 처리를 함께 담아야 한다.

그리고 **검사를 만든 직후가 가장 위험하다.** 방금 만들었으니 잘 안다고 믿지만,
그 검사가 무엇을 놓치는지는 아직 한 번도 시험되지 않았다. §21 이 "일부러
위반을 만들어 확인한다" 고 적었는데, 여기서는 위반의 종류를 하나만 상상했다.

## §34. 끝난 뒤에 잰 환경은 측정 중 환경이 아니다

**2026-09-13**

### 증상

처리율이 32 → 16자/초로 떨어졌다. 배치별 시간이 131.8 · 113.0 · 112.3 ·
167.4 · 335.4 초로 뒤로 갈수록 폭증했고 웜업도 65 → 97 → 140 → 155 초로 계속
늘었다. 프롬프트는 오히려 짧아졌으므로 코드로 설명되지 않았다.

VRAM 압박에 따른 CPU 오프로딩을 의심해 `nvidia-smi` 와 `ollama ps` 를 쳤다.
**모델은 이미 언로드되어 있었고 VRAM 은 480MiB 만 쓰고 있었다.** 온도 51도,
클럭 1455MHz 로 전부 정상 유휴였다.

### 원인

진단을 측정이 끝난 뒤에 했다. `keep_alive` 가 지나 모델이 내려간 상태이므로
그 수치는 "지금 아무것도 안 돌고 있다" 는 사실만 말한다. **가설을 확인하지도
기각하지도 못한다.**

한 번 더 사후에 재는 것은 같은 함정이다. 이상이 재현될 때 사람이 마침 그
자리에 있어야 하고, 없으면 또 끝난 뒤에 재게 된다.

### 조치

`bench_golden.py` 가 배치마다 환경을 찍어 결과와 함께 남긴다 — VRAM, GPU 온도 ·
클럭, `ollama ps` 의 PROCESSOR 칸, 시스템 여유 메모리와 스왑. 오프로딩이나 스왑이
보이면 콘솔에도 그 자리에서 표시한다.

**도구가 없으면 조용히 건너뛴다.** 이 기록은 측정을 돕는 부속이지 측정의
전제가 아니다. `nvidia-smi` 가 없는 기계에서 벤치가 못 돌면 부속이 본체를
막는 것이다. 명령이 없을 때와 실패할 때 양쪽을 테스트로 고정했다.

지문에는 넣지 않는다. 모델이 보는 것이 아니므로 재측정을 요구해서는 안 된다
(§22).

원인은 아직 모른다. 다만 다음에 이상이 나타나면 사후 추측이 아니라 기록을
본다.

### 배운 것

**관측 시점이 관측 대상의 일부다.** "무엇을 재는가" 만 정하고 "언제 재는가" 를
정하지 않으면, 잰 값이 무엇에 대한 값인지 알 수 없다. §27 이 재현 절차에서
빠진 조건은 우연이 된다고 적었는데, 시점도 그 조건의 하나다.

그리고 **사람이 그 자리에 있어야 하는 진단은 진단 절차가 아니다.** 이상은
예고 없이 나타나므로 기록은 상시로 남긴다. §31 이 플래그를 사람이 세우게 두면
안 된다고 적은 것과 같은 이유다.

## §35. temperature 0 은 같은 하드웨어 배치에서만 결정적이다

**2026-09-13**

### 증상

§34 에서 붙인 환경 기록이 첫 실행에서 답을 냈다. 다섯 배치 모두
`38%/62% CPU/GPU` 로 찍혔고 여유 메모리가 173MB, 스왑 사용이 6.4GB 였다.
**모델이 부분 오프로딩된 상태였다.**

그런데 속도만 달라진 것이 아니었다. **같은 지문 · 같은 `temperature 0` 인데
위반이 2 → 4 로 늘었다.** 3차에서 사라졌던 `consumer` 와 `latency` 가 돌아왔다.

### 원인

오프로딩되면 일부 레이어가 CPU 커널로 계산된다. CPU 와 GPU 는 부동소수점 누적
순서가 달라 같은 입력에 미세하게 다른 값이 나오고, 그 차이가 상위 후보의 순서를
뒤집으면 토큰 선택이 갈린다.

`temperature 0` 은 **주어진 확률 분포에서 최대값을 고르라는 뜻**이지 분포 자체가
항상 같다는 보장이 아니다. 분포를 만드는 연산이 달라지면 결과도 달라진다.

이 저장소는 `engine.py` 첫머리에 "temperature 0 + 고정 seed 를 쓴다 … 캐시가
최초 결과를 영구 고정하므로" 라고 적어 두었다. 맞는 말이지만 **조건이 빠져
있었다.** 같은 배치에서 돌 때만 그렇다.

병목이 GPU 가 아니었던 것도 같이 드러났다. VRAM 은 6144 중 1.6GB 가 남아
있었다. 모자란 것은 시스템 RAM 이었다 — 모델을 GPU 로 올리려면 먼저 RAM 으로
읽어야 하는데 읽을 자리가 없었다. **다른 WSL 터미널의 작업이 같은 커널과 페이지
캐시를 쓴다는 것을 계산에 넣지 않았다.**

### 조치

`baseline.json` 의 `violations` 에 `condition: "100% GPU · 오프로딩 없음"` 을
달았다. 값만 적고 그 값이 성립하는 조건을 적지 않으면 다음에 다른 숫자가 나왔을
때 무엇이 틀렸는지 모른다.

러너가 오프로딩을 감지하면 보고 끝에 경고한다 — **속도도 위반 수도 그 실행의
값으로 쓸 수 없다**는 것과, 볼 곳이 GPU 가 아니라 시스템 RAM 이라는 것까지.

`ollama ps` 파싱도 고쳤다. 비율이 PROCESSOR 앞 칸에 따로 있어서 칸 하나만
집으면 `38%/62%` 를 잃고 `CPU/GPU` 만 남는다. 오프로딩 여부는 문자열이 아니라
불로 남겨 기록을 읽는 쪽이 다시 파싱하지 않게 했다.

### 배운 것

**재현성의 조건은 소프트웨어에서 끝나지 않는다.** 씨앗과 온도를 고정하면
결정적이라고 믿었는데, 그 아래에 연산 장치라는 층이 하나 더 있었다. 기준선을
만들 때 "무엇을 고정했는가" 를 세면서 고정하지 못한 것을 세지 않았다.

그리고 **환경 기록이 하루치 추측을 한 번에 끝냈다.** 그 전까지 세 번은 사후에
재고 가설을 세웠고 전부 GPU 를 향했다. 기록을 남기기 시작한 첫 실행에서 GPU 가
아니라 RAM 이라는 것이 드러났다. §34 를 쓸 때는 "다음에 이상이 나타나면" 이라고
적었는데 다음이 바로 왔다.

---

## §36. 도달할 수 없는 조건을 기준선에 박으면 영원히 stale 이다

**2026-09-13**

### 증상

§35 에서 "시스템 RAM 부족" 을 원인으로 적고 `condition: "100% GPU · 오프로딩
없음"` 을 기준선에 걸었다. 메모리를 비우고 다시 쟀다 — 여유 4.8GB, 스왑 97MB.
**그런데도 오프로딩됐다**(24%/76% CPU/GPU).

### 원인

RAM 가설이 틀렸다. VRAM 은 6144 중 4732 만 쓰여 1.4GB 가 남아 있었는데도 전부
올라가지 않았다. ollama 는 가중치만이 아니라 **KV 캐시와 컴퓨트 버퍼도 VRAM 에
넣는다.** 4.6GB 모델에 컨텍스트 버퍼를 더하면 6GB 를 넘으므로 일부 레이어가
CPU 에 남는다. **이 기계에서 오프로딩은 결함이 아니라 정상 상태다.**

더 나쁜 것은 조건을 적은 방식이다. `100% GPU` 가 이 기계에서 가능한지 확인하지
않고 적었다. 도달할 수 없는 조건을 걸면 기준선은 영영 채워지지 않는다.

한편 이번 실행이 오늘 가장 빨랐다(35자/초, 배치 74.9~88.4초로 고르다). 느렸던
것은 오프로딩 때문이 아니라 메모리 압박 때문이었다. **두 가지를 하나로 묶어
본 것이 §35 의 실수다.**

위반은 4 로 나왔다. 배치가 크게 다른 두 실행(38%/62% 와 24%/76%)에서 같은 값이
나왔으므로 채택했다. 3차의 2 는 환경 기록 이전이라 배치를 모르고 재현되지도
않았다 — 이력으로만 남긴다.

### 조치

기준선의 `condition` 을 실측 배치 `24%/76% CPU/GPU` 로 적었다. 러너가 이번
실행의 배치를 기준선과 대조해, 실행 중에 바뀌었거나 기준선과 다르면 경고한다.
**오프로딩 여부가 아니라 배치 일치를 본다.**

`ollama ps` 의 컨텍스트도 함께 남긴다. 왜 전부 올라가지 않았는지를 사후에 다시
추측하지 않기 위해서다.

### 배운 것

**조건을 적기 전에 그 조건이 달성 가능한지 확인한다.** 이상적인 상태를 적어
두면 엄격해 보이지만, 도달할 수 없으면 검사가 아니라 영구 경고가 된다.
§19 가 "기준선을 모르고 정한 임계값은 검사가 아니다" 라고 적었는데, 여기서는
기준선이 아니라 **환경의 한계**를 모르고 정했다.

그리고 **두 증상을 한 원인으로 묶기 전에 각각이 따로 움직이는지 본다.**
느린 것과 오프로딩이 같이 나타나 하나로 봤는데, 오프로딩된 채로 가장 빠른
실행이 나오면서 갈렸다. 함께 나타난 것이 같은 원인이라는 보장은 없다.

## §37. 틀린 원인을 단정하는 메시지는 침묵보다 나쁘다

**2026-09-13**

### 증상

WSL 이 재시작되면서 ollama 가 죽어 있었다. 벤치를 돌리니 이렇게 나왔다.

```
워커에 닿지 못했다: HTTP Error 502: Bad Gateway
  bash tools/run_worker.sh & 로 띄운다
```

**워커에는 닿았다.** 502 를 돌려줬으니 살아 있다. 죽은 것은 ollama 다. 안내를
따라 워커를 다시 띄우면 502 가 또 난다.

같은 자리에서 `doctor.sh` 는 `SKIP ollama 서버 미기동` 이라 적고 "이상 없음"
으로 끝냈다. `.env` 의 `ENGINE` 이 `local` 인데도 그랬다.

### 원인

`HTTPError` 는 `URLError` 의 하위 클래스다. `except urllib.error.URLError` 가
둘을 함께 잡는데 메시지는 연결 실패만 상정하고 있었다. **뭉뚱그린 것은 예외고,
단정한 것은 메시지다.**

`doctor.sh` 쪽은 무엇을 건너뛸지를 설정과 무관하게 정했다. ollama 가 없는 것은
`ENGINE=echo` 에서는 건너뛸 일이고 `ENGINE=local` 에서는 고장이다. 같은 사실이
설정에 따라 다른 판정을 받아야 하는데 한 가지로만 보았다(§22 의 재발).

덧붙여 `_ollama` 의 타임아웃이 180초였다. 실측 배치가 335초까지 갔으므로 느린
날에는 번역이 아니라 타임아웃이 결과가 된다. 실측이 상한을 넘긴 것을 여태
아무도 보지 않았다.

### 조치

`explain_failure` 가 502 · 401 · 연결 실패를 갈라 안내한다. 502 면 "워커는 살아
있다" 를 먼저 말하고 엔진 쪽을 가리킨다. 응답 본문의 `error` 코드도 함께
보여준다 — 본문이 JSON 이 아니어도 안내는 나간다.

`doctor.sh` 는 `ENGINE=local` 일 때 ollama 미응답을 FAIL 로 올린다. 다른
엔진에서는 "필요 없다" 를 붙여 건너뛴다.

`OLLAMA_TIMEOUT` 을 환경변수로 빼고 기본을 700초로 두었다 — 실측 최대의 두
배다. 확장의 `TIMEOUT_MS` 는 200초 그대로 둔다. 그것은 **사용자가 기다리는
시간**이라 성격이 다르고, 확장은 배치가 작아 이 상한에 먼저 닿지 않는다.

### 배운 것

**메시지가 원인을 단정하려면 원인을 알아야 한다.** "닿지 못했다" 는 관찰이
아니라 추론이었고 틀렸다. 확신이 없으면 증상만 적는 편이 낫다 — 틀린 안내는
사람을 엉뚱한 곳으로 보내 시간을 두 배로 쓰게 한다.

그리고 **예외 계층을 뭉뚱그릴 때는 메시지도 함께 뭉뚱그렸는지 본다.** 넓게
잡는 것 자체는 편의이고 잘못이 아니다. 잘못은 넓게 잡아 놓고 좁은 경우만
상정해 말하는 것이다.

세 번째로 **상한은 실측과 대조한다.** 180초는 짜 놓을 당시에는 넉넉했고, 실측이
335초에 닿은 뒤에도 그대로 남아 있었다. 숫자를 정한 근거가 바뀌면 숫자도 다시
본다.

## §38. 팝업을 다는 순간 아이콘 클릭 리스너가 죽는다

**2026-09-13**

### 증상

설정 UI 를 옵션 페이지로 만들려다 팝업 쪽이 사용자 편의가 낫다는 판단이
나왔다. 그런데 이 저장소는 아이콘 클릭이 **권한 요청과 주입을 전부** 하고
있었다. 팝업을 그냥 달면 그 경로가 통째로 죽는다.

### 원인

크롬 문서가 명시한다 — 액션에 팝업이 지정되면 `onClicked` 이벤트는 보내지지
않는다. 팝업 열기가 클릭을 가져가기 때문이다.

한편 `permissions.request` 는 사용자 제스처 안에서만 성립한다. 그래서 "팝업을
달면 권한 요청을 못 한다" 로 읽기 쉬운데, **팝업의 버튼 클릭도 사용자
제스처다.** 크롬 문서의 예시가 정확히 버튼의 클릭 핸들러 안에서 요청한다.

제약은 §13 이 적은 것과 같다. 요청 전에 `await` 가 하나라도 있으면 문맥을
잃는다. 크롬 토론에서도 `permissions.contains` 를 먼저 부르는 순간 같은 오류가
난다고 하며, **UI 가 초기화될 때 미리 부르라**고 권한다. 이 저장소가 §13 에서
스스로 도달한 결론과 같다.

### 조치

권한 요청과 주입을 팝업으로 옮겼다. 팝업이 **열릴 때** 탭과 권한 상태를 미리
조회해 두고, 버튼 클릭 핸들러에서는 콜백 형태로 요청만 한다. 승인 뒤 주입은
제스처가 필요 없으므로 메시지로 background 에 맡긴다.

`background.js` 의 `onClicked` 리스너를 **지웠다.** 발화하지 않는 코드를
남기면 다음 사람이 그것이 도는 줄 안다. `onUpdated` 자동 주입은 그대로 둔다.

판정을 `state.js` 순수 함수로 떼어 `node:test` 로 검증한다. 확장에 테스트가
없어 결함이 사람 눈에만 걸렸는데(PLAN §2-1 #41), 러너를 고르는 일로 시작을
미루지 않으려고 Node 내장을 썼다 — 의존성도 `package.json` 도 없다.

`doctor.sh` 의 manifest 검사를 팝업까지 넓혔다. `default_popup` 이 가리키는
파일과 그 안에서 부르는 자산이 없으면 아이콘을 눌러도 빈 창이 뜬다 — 조용히
죽는 자리다. `sync_ext.sh` 는 `tests/` 를 내보내지 않는다. 테스트는 배포물이
아니다.

### 배운 것

**API 를 바꾸면 그 API 가 떠받치던 것을 센다.** 팝업은 UI 결정처럼 보였지만
실제로는 권한 · 주입 · 제스처가 딸려 있었다. 겉보기 층위의 변경이 아래 층을
건드리는지 먼저 본다.

그리고 **"못 한다" 로 보이는 제약은 조건을 확인하고 판단한다.** 팝업에서
권한 요청이 안 된다고 넘겨짚었으면 옵션 페이지로 갔을 것이다. 제약은
"제스처 안에서" 였고 팝업의 클릭이 그 조건을 만족한다. 제약의 문구를 읽지
않고 결론만 기억하면 할 수 있는 것을 포기한다.

## §39. 매치 조건과 수집 대상이 어긋나면 이기고도 진다

**2026-09-13**

### 증상

`standard` 어댑터를 실사이트에 올리기 전에 읽다가 찾았다. 이 계층은 한 번도
실행된 적이 없다(§17).

- `match` 는 `[role=radiogroup]` · `[role=listbox]` · `form input[type=radio]` 를 본다
- `collect` 는 `[role=radiogroup]` 과 `[role=listbox]` 만 순회한다

**ARIA role 없이 네이티브 라디오만 쓰는 폼에서 이 어댑터가 선택되고도 그룹을
하나도 만들지 못한다.**

### 원인

어댑터는 배타 선택이다. `priority` 가 높은 것이 이기면 아래 계층은 돌지 않는다.
그래서 매치 조건은 **"다룰 수 있는가" 여야 하는데 "관심 있는가" 로 적혀
있었다.**

더 나쁜 결과가 딸려 있었다. `genericCollect` 의 수집 태그 목록에 `label` 이
없다. 그래서 그 경우 보기 라벨을 **아무도 수집하지 않는다.** Layer 0 이
이겼으면 최소한 본문은 모았을 텐데, Layer 1 이 이기고 아무것도 못 모은다.
§11 이 "상위 계층은 하위 계층보다 나빠질 수 있다" 고 적은 바로 그 자리이며,
그때는 위임으로 막았고 이번에는 매치 조건이 새로 뚫었다.

### 조치

`collect` 가 네이티브 라디오도 다룬다. **같은 `name` 을 가진 라디오가 한
그룹이라는 것은 HTML 표준이므로** 사이트 지식이 아니고 Layer 1 에 있어도 된다.
라벨은 감싸는 `label` 이나 `label[for]` 로 찾는다.

라디오가 하나뿐인 `name` 은 그룹으로 만들지 않는다. 묶을 것이 없는데 그룹을
만들면 배치 번역이 얻는 것 없이 형태만 남는다.

**테스트는 붙이지 못했다.** `collect` 는 DOM 조작이 본체라 떼어낼 순수 부분이
없다. 스텁을 만들 수도 있으나 스텁이 실제 브라우저와 어긋나면 거짓 안심을
준다 — 조용히 아무것도 하지 않는 검사가 그렇게 생긴다(§21). DOM 러너를 정하는
일은 PLAN §2-1 #41 로 남긴다.

### 배운 것

**배타 선택에서 매치 조건은 능력의 선언이다.** "이 페이지에 아는 것이 있는가"
가 아니라 "이 페이지를 하위 계층보다 낫게 다룰 수 있는가" 를 물어야 한다. 전자로 적으면 관심만 있고 능력은 없는 경우에 이겨 버린다.

그리고 **한 번도 실행되지 않은 코드는 읽어서 찾을 수 있는 결함부터 찾는다.**
실사이트에 올리는 것이 검증이지만, 올리기 전에 읽는 것으로도 이 어긋남은
보였다. 실행이 유일한 검증 수단은 아니다.

## §40. 영구 오염을 막는 규칙이 일회성 지정까지 막고 있었다

**2026-09-13**

### 증상

픽스처를 빠르게 보려고 `ENGINE=echo bash tools/run_worker.sh` 로 띄웠는데
번역이 느렸다. `/health` 를 치니 `"engine":"local"` 이었다. **앞에 붙인 지정이
조용히 무시됐다.**

### 원인

`run_worker.sh` 가 `.env` 를 `set -a; . ./.env; set +a` 로 읽는다. 소싱은
파일의 값을 무조건 덮어쓰므로 이미 환경에 있던 값이 진다. 스크립트 주석에도
"우선순위는 셸 > 파일이 아니라 파일이 기본값" 이라고 적혀 있었다 — 알고 만든
동작이다.

그 근거는 D-0066 이다. 프로젝트 설정을 셸에 `export` 해 두면 `.env` 가 조용히
무시되므로, 파일을 정본으로 두려 했다. **막으려던 것은 `~/.bashrc` 에 박아
두는 영구 오염이고, 그것은 `doctor.sh` 가 이미 따로 검사한다.** 한 줄 앞에
붙이는 일회성 지정은 다른 일인데 같이 막혔다.

대가는 작지 않았다. 한 번만 다른 엔진으로 띄우려면 `.env` 를 고쳤다 되돌려야
하고, 되돌리는 것을 잊으면 다음 측정이 오염된다. 오늘 이미 오염된 측정으로
한나절을 썼다(§35 · §36).

같은 한 줄이 여섯 스크립트에 복제되어 있던 것도 함께 드러났다.

### 조치

`tools/lib/env.sh` 에 로더를 모으고 여섯 곳이 그것을 부른다. **이미 환경에
있는 키는 덮지 않는다.**

파일을 직접 파싱하지 않는다. `.env` 는 셸 문법으로 읽히므로 따옴표와 확장을
흉내 내면 소싱과 결과가 갈린다. 소싱은 그대로 두고 **미리 있던 키만 되돌린다.**
설정 여부는 `${!k+x}` 로 묻는다 — 빈 문자열로 설정된 것도 설정이다.

`doctor.sh` 가 일회성 지정이 먹는지 검사한다. 셸이라 pytest 가 보지 못하는
자리이고, 옛 방식으로 되돌려 잡히는 것을 확인했다.

### 배운 것

**규칙을 만들 때 그 규칙이 함께 막는 것을 센다.** "파일이 정본" 은 옳았고
영구 오염을 막는 데도 맞았다. 다만 그 문장이 일회성 지정까지 덮는다는 것을
보지 않았다. 금지의 범위는 의도가 아니라 문장이 정한다(§22 와 같은 결).

그리고 **불편이 오래가면 그것은 취향이 아니라 결함이다.** `.env` 를 고쳤다
되돌리는 일을 여러 번 하면서도 그 절차 자체를 의심하지 않았다. 같은 수고가
반복되면 도구를 본다.

## §41. 위생은 층을 나눠 재고 입구는 지우지 않는다

**2026-09-13**

### 증상

푸시 뒤에 저장소를 치우는 절차가 thoth 에 없었다. 다른 저장소에는 같은 성격의
파이프라인이 있는데 이쪽으로 넘어온 적이 없어, 잔재가 쌓여도 아무도 세지
않았다. 오늘만 `__pycache__` 가 셋, `.pytest_cache` 가 하나 남았고 다운로드
폴더에는 적용이 끝난 패치가 쌓였다.

### 원인

치우는 일을 사람의 기억에 맡겼다. 기억은 잊히고, 잊힌 것은 재지지 않는다.
**재지 않으면 더러운지도 모른다.**

### 조치

층을 셋으로 나누고 도구를 셋 둔다. 입구는 `tools/janitor.sh` 하나다.

| 층 | 도구 | 보는 것 |
|---|---|---|
| 기계 | `~/.local/bin/hygiene.sh` | 홈 · 마운트 · `.venv` 셔뱅 · `.env` |
| 저장소 | `tools/tidy.py` | 캐시 · 파이썬 산출물 · 루트 잔재 |
| 레이크 | `tools/sweep.py` | 다운로드에서 근거를 잃은 패치 |

설계 원칙 다섯을 지킨다.

**㉠ 묶는 이유는 하나뿐이다 — 하나가 죽어도 나머지가 돈다.** `/mnt/c` 가 빠지면
`sweep` 이 실패하는데, 그때 `tidy` 까지 멈추면 저장소를 못 치운다. 각 단계는
실패해도 다음으로 넘어간다.

**㉡ 합치면 층 구분이 사라진다.** 어느 층이 더러운지 못 가리면 기계가 더러운데
저장소를 뒤지는 일이 난다. 입구만 하나고 실행은 합치지 않는다.

**㉢ 실패를 0건으로 적지 않는다.** 못 잰 것과 깨끗한 것은 다르다. `sweep` 은
`WIN_DOWNLOADS` 에 닿지 못하면 종료 코드 2 로 끝나고 입구가 `못 잼` 으로 적는다.
§27 이 "재현 절차에서 빠진 조건은 우연이 된다" 고 적은 것과 같은 규율이다.

**㉣ 입구는 지우지 않는다.** `--yes` 를 받지 않는다. 무엇을 왜 지우는지는 각
도구가 알고 껍데기는 모른다. 근거를 찾고 지우는 것과 지울 만해 보여서 지우는
것은 다르다. `sweep` 의 근거는 역적용이다 — `git apply --check -R` 이 성공하면
그 패치는 이미 저장소에 들어가 있다(§29 에서 쓴 기법). 날짜나 이름으로
추측하지 않는다.

**㉤ 기계 도구만 저장소 밖에 둔다.** 기계를 보는 도구를 저장소에 두면
저장소마다 사본이 생긴다. 없으면 그 줄만 건너뛴다.

번역 캐시는 세기만 하고 지우지 않는다. 지우면 재번역이고 과금 엔진에서는
재과금이다(§5). **위생의 목적은 자리를 비우는 것이지 값을 버리는 것이 아니다.**
`.venv` 도 마찬가지다 — `.gitignore` 에 있다고 다 잔재는 아니다.

`doctor.sh` 가 저장소 층 건수를 보고한다. **FAIL 로 올리지 않는다** — 잔재가
쌓인 것은 커밋을 막을 일이 아니고, 막으면 급할 때 넘기는 버릇이 든다. 그렇다고
조용히 지나가면 아무도 치우지 않으므로 SKIP 으로 적는다.

### 배운 것

**세지 않는 것은 관리되지 않는다.** 치우는 절차가 없어서가 아니라 더러운지
아는 방법이 없어서 쌓였다. 도구를 만드는 일의 절반은 재는 일이다.

그리고 **입구를 하나로 두는 것과 실행을 합치는 것은 다르다.** 편의를 위해
입구를 모으되 층은 끝까지 나눠 둔다. 합치는 순간 어느 층이 실패했는지,
어느 층이 더러운지가 한 숫자에 뭉개진다.

## §42. 화장실을 같이 써도 내 것은 가릴 수 있다

**2026-09-13**

### 증상

위생 도구를 만들면서 층을 셋으로 나누고 저장소 층에 `tidy.py` 를 두었다.
그런데 실측해 보니 저장소가 쌓은 것은 **300KB** 였고, 기계에 쌓인 것은 10GB
였다 — `~/.cache/uv` 5.5G, `~/.ollama/models` 4.5G.

**도구가 대상보다 비쌌다.** 300KB 를 치우려고 도구 셋과 입구 하나를 만들었다.

그리고 5.5G 를 두고 "계정 하나에 하나이니 이 저장소가 손댈 자리가 아니다" 로
넘겼다. 맞는 말이지만 질문에 답한 것이 아니다. 물은 것은 **내 것만 골라낼 수
있는가** 였다.

### 원인

층을 나눈 기준이 **소유가 아니라 위치**였다. 기계 층 · 저장소 층으로 가르면
`~/.cache/uv` 는 통째로 기계 층이 되고, 그 안에 이 저장소가 받게 한 것이 섞여
있어도 손댈 수 없게 된다.

uv 캐시는 어느 프로젝트가 받게 했는지를 기록하지 않는다. 그래서 "못 고른다" 로
결론지었는데, **`uv.lock` 이 무엇을 요구하는지는 안다.** 이웃 저장소의 lock 과
빼면 이 저장소만 쓰는 것이 남는다. 기록이 없다고 판정이 불가능한 것은 아니었다.

### 조치

층을 둘로 줄이고 `tidy.py` 와 `janitor.sh` 를 버렸다. 저장소 층은 도구 없이
`doctor` 가 건수만 보고한다 — `git clean -Xfd` 가 이미 있다.

`sweep.py` 가 셋을 본다.

| 대상 | 판정 근거 |
|---|---|
| `/tmp` 흔적 | 이름. 그것을 쓰는 프로세스가 떠 있으면 남긴다 |
| 수신함의 패치 | 역적용(§29). 적용이 끝난 것만 지운다 |
| uv 캐시 | `uv.lock` 차집합. **이웃과 겹치는 것은 남긴다** |

**겹치는 것은 남긴다.** `fastapi` 를 이웃도 쓰면 그 캐시는 공유 자산이고,
지우면 남의 재설치가 느려진다. 내 것이 아닌 것을 치우는 것은 위생이 아니다.

이웃은 `uv.lock` 을 가진 디렉터리만 센다. 부모 아래의 모든 폴더를 이웃으로
세면 작업 사본이 섞여 판정이 흔들린다. 로컬 프로젝트 자신은 `pyproject.toml`
의 `name` 으로 빼낸다 — 캐시된 배포판이 아니다.

이웃을 하나도 찾지 못하면 **못 잼**이다. 전부 내 것이라고 단정하지 않는다.
그렇게 단정하면 남의 것을 지운다.

`~/.ollama/models` 4.5G 는 자산이라 손대지 않는다. `doctor` 가 채택 모델만
남아 있는지 이미 본다.

### 배운 것

**"내 것이 아니다" 와 "가릴 수 없다" 는 다른 말이다.** 공유 자원이라는 이유로
손을 떼면 이 저장소가 늘린 몫도 영영 남는다. 가릴 방법이 있는지 먼저 묻는다.

그리고 **도구의 크기는 대상의 크기가 정한다.** 층을 셋으로 나눈 것은 남의
저장소에서 옳았던 구조를 그대로 가져온 것이고, 이쪽 실측과 맞지 않았다.
설계를 옮길 때는 그 설계가 서 있던 수치도 같이 본다.

## §43. 알고 있는 목록은 언젠가 하나를 빠뜨린다

**2026-09-13**

### 증상

한 세션에서 같은 종류를 세 번 빠뜨렸다. 문서 대조를 두 번, 푸시 뒤 위생을 한
번이다. 두 번째로 지적받은 뒤 "앞으로 대조하고 간다" 고 적어 두었는데 그다음에
또 빠뜨렸다.

`sweep.py` 에도 결함이 있었다. 직접 부르면 수신함을 `못 잼` 으로 보고했다.

### 원인

순서가 **사람 머리에만** 있었다. `doctor` · 문서 대조 · 커밋 · 푸시 · 위생은
매번 같은 순서로 도는데 그것을 아는 것은 기억뿐이었다. 안내 문구를 도구에
넣었지만 그것도 읽고 기억하는 구조라 같은 종류다.

빠뜨린 셋을 세어 보니 **전부 조건 없이 매번 도는 단계**였다. 조건부 단계
(패치 적용 · `.env` 키 추가 · 확장 동기화)는 한 번도 빠뜨리지 않았다 — 그쪽은
각 도구가 그 자리에서 알려주기 때문이다.

`sweep.py` 쪽은 다른 결이다. `doctor` 와 `apply_patch` 는 셸 로더를 거쳐
`.env` 를 읽는데 이 도구는 스스로 읽지 않았다. **도구가 자기 입력을 스스로
챙기지 않으면 부르는 방법마다 결과가 달라진다.**

### 조치

`tools/ship.sh` 가 무조건 단계 넷을 묶는다 — `doctor` → 문서 대조 → 커밋 →
푸시 안내. 조건부 단계는 넣지 않았다. 이미 각 도구가 알려주고, 넣으면 도구가
상황을 판단해야 해서 커진다.

**문서 대조는 기계가 볼 수 있는 만큼만 본다.** 내용이 코드와 맞는지는 사람이
본다(`check_docs.py` 머리말). 기계가 아는 것은 **안 봤다는 사실**이다 —
`tools/` · `worker/` · `extension/` 이 바뀌었는데 `docs/` 와 `README` 가 그대로면
멈추고 묻는다.

**푸시는 자동으로 하지 않는다.** 무엇이 나가는지 보여주고 사람이 친다. 자동으로
미는 도구는 사고가 난다. `--no-verify` 도 받지 않는다 — 급할 때 넘기는 문을
만들면 급할 때 넘긴다. 커밋 메시지는 인자로 받고 지어내지 않는다.

`doctor` 는 `ship` 을 모른다. 상위 도구가 하위 검사 사슬에 들어가면 순환이
된다. `doctor` 에 `--ship` 같은 인자를 두지 않는 것이 그 경계다.

`sweep.py` 에 자체 `.env` 로더를 넣었다. 우선순위는 `tools/lib/env.sh` 와 같다
— 셸에 앞세운 지정이 이긴다(§40). 두 로더가 다르게 굴면 그것이 또 하나의
갈림이다.

`doctor` 의 비밀값 검사를 SSD 까지 넓혔다. 기존 셋은 전부 `git` 에 묻기 때문에
저장소 밖이 구조적으로 시야 밖이었고, 실제로 `$THOTH_SSD_ROOT/.aws/credentials`
가 장기 액세스 키를 담은 채 남아 있었다. **DrvFs 는 유닉스 권한이 붙지 않아
`600` 을 줄 수 없으므로 "권한을 고쳐라" 가 아니라 "두지 마라" 가 맞는 검사다.**
이름으로만 찾고 내용은 읽지 않는다 — 검사가 비밀을 읽을 이유가 없다.

### 배운 것

**빠뜨리는 것은 조건부가 아니라 무조건 쪽이다.** 조건부 단계는 그 조건이
닥칠 때 도구가 알려주지만, 매번 도는 단계는 알려 줄 계기가 없어 기억에만
남는다. 자동화할 자리를 고를 때 "복잡한 것" 이 아니라 "매번 같은 것" 을 본다.

그리고 **다짐은 조치가 아니다.** 두 번째 지적 뒤에 문장을 적었고 그다음에 또
빠뜨렸다. 문장으로 고쳤다고 적은 것은 고친 것이 아니다.

## §44. 못 지운 것을 지운 수에 넣으면 그 수를 보고 한 판단도 틀린다

**2026-09-13**

### 증상

`sweep --fix` 가 `2건 지웠다` 로 끝났는데 출력 끝에 이런 줄이 섞여 있었다.

```
process running? You can set `UV_LOCK_TIMEOUT` to increase the timeout.
```

**uv 캐시 정리가 실패했는데 실패라고 적히지 않았다.** 합계 2건은 `/tmp` 와
수신함이고 캐시는 한 건도 못 지웠다.

### 원인

둘을 한꺼번에 어겼다.

`uv cache clean` 의 **종료 코드를 보지 않았다.** 출력의 마지막 줄만 찍었는데,
성공했을 때는 `Removed 2153 files` 가 마지막 줄이라 잘 보였고 실패했을 때는
여러 줄 중 하나만 남아 무슨 일인지 알 수 없었다. §41 ㉢ 에 "실패를 0건으로
적지 않는다" 고 적고 그 규율을 스스로 어겼다.

그리고 **못 지운 것을 지운 수에 넣었다.** 합계가 실제로 한 일과 달라졌다.

원인 자체는 결함이 아니었다. 이웃 저장소가 `uv run` 으로 돌고 있었고 그것이
캐시 락을 쥐고 있었다. 캐시는 계정 하나에 하나이므로 **남이 쓰는 중에는 비키는
것이 맞다.** 문제는 비켰다는 사실을 적지 않은 것이다.

### 조치

종료 코드를 본다. 실패하면 `못 잼` 으로 적고, 출력 끝 세 줄과 `pgrep -a uv` 로
찾은 쥐고 있는 프로세스를 함께 보여준다. 종료 코드도 2 로 나간다.

합계에서 캐시를 뺐다. `/tmp` 와 수신함만 세고 캐시는 따로 적는다 — **건수가
아니라 패키지 수라 단위도 다르다.**

### 배운 것

**세는 것과 쓴 것이 같아야 한다.** 합계가 실제로 한 일과 다르면 그 합계를 보고
한 다음 판단이 틀린다. 여기서는 "다 치웠구나" 로 읽혔고 실제로는 캐시가
그대로였다.

그리고 **규율을 적은 사람이 그 규율을 어긴다.** §41 에 "실패를 0건으로 적지
않는다" 를 적은 것이 같은 날이었다. 적는 것과 지키는 것은 다른 일이고, 지키게
하는 것은 문장이 아니라 코드다(§43 과 같은 결).

## §45. 번호가 실재해도 내용이 맞는 것은 아니다

**2026-09-13**

### 증상

세션 끝에 도구와 문서를 대조하다 `bench_engine.sh` 가 문서 어디에도 없는 것을
발견했다. 파일을 열어 보니 주석이 `PLAN §5 #37` 을 가리키는데 **#37 은 "어댑터
자동 생성"** 이다. 이 도구는 번역 엔진을 재는 물건이라 전혀 다른 항목이다.

### 원인

같은 날 `§3 #37` 을 `§5 #37` 로 고쳤다. 절 번호가 틀린 것을 보고 절만 맞췄고
**항목이 맞는지는 보지 않았다.** `#35` 를 지우면서 번호가 밀린 줄 알았는데,
애초에 가리키는 항목 자체가 잘못돼 있었다.

§29 에서 만든 `check_refs` 는 번호가 PLAN 에 실재하는지만 본다. 실재하는 번호를
가리키면 통과하므로 **엉뚱한 항목을 가리키는 것은 잡지 못한다.** 검사가 무엇을
놓치는지 그때 적어 두지 않았다.

### 조치

`#36`(배포본 엔진)으로 고쳤다. 주석에 한동안 틀린 곳을 가리켰다는 것과, 이
부류는 사람이 본다는 것을 함께 적었다.

`README` 의 점검 목록에 `bench_engine.sh` 와 `scan.sh` 를 넣었다. 문서에 한 번도
나오지 않는 도구는 다음 사람이 있는 줄도 모른다.

**자동 검사를 더 만들지 않는다.** 참조가 가리키는 항목이 내용상 맞는지는 기계가
볼 수 없다. `check_docs.py` 머리말이 "검사 대상은 문체와 구조뿐이고 내용은
사람이 본다" 고 적은 그 경계다.

### 배운 것

**검사를 만들 때 무엇을 놓치는지도 같이 적는다.** `check_refs` 가 죽은 참조를
잡아 준 것이 오늘만 두 번이라 그 검사를 믿게 됐는데, 믿는 만큼 그것이 보지
않는 자리가 넓어진다. 잡는 것을 적으면 놓치는 것도 적어야 한다.

그리고 **틀린 것을 고칠 때는 그것이 왜 틀렸는지까지 본다.** 절 번호가 안 맞아
절만 고쳤다. 그 참조가 원래 무엇을 가리키려 했는지 물었으면 그때 잡혔다.

## §46. 등급이 하나뿐이면 모든 검사가 최악의 검사와 같은 힘을 갖는다

**2026-09-14**

### 증상

문서 세 줄을 고친 커밋이 막혔다.

```
FAIL ENGINE=local 인데 ollama 가 응답하지 않는다
멈춘다 — doctor 가 FAIL 했다
```

번역을 돌릴 일이 없는 커밋이었다. 통과시키려면 4.5GB 모델을 올리거나 `.env`
를 고쳐야 했다. **검사가 목적을 배반했다.**

### 원인

`doctor` 의 보고 함수가 셋인데 의미는 둘뿐이었다 — `ok` · `skip` 은 통과,
`no` 는 막는다. 그래서 "저장소가 틀렸다" 와 "지금 작업하려면 손봐야 한다" 가
같은 등급을 받았다.

전날 §37 에서 이 검사를 `SKIP` 에서 `FAIL` 로 올렸다. 그때는 옳았다 — `doctor`
가 "이상 없음" 을 내고 곧바로 벤치가 502 로 죽었기 때문이다. 다만 **올릴 수
있는 자리가 `FAIL` 하나뿐이라 필요 이상으로 올라갔다.**

같은 자리가 이미 더 있었다. 미채택 모델 · SSD 모델 잔재 · SSD 경로 없음이
전부 `FAIL` 인데 셋 다 커밋을 막을 일이 아니다. **ollama 하나만 고치면 같은
일이 또 난다.**

### 조치

`warn` 등급을 넣었다. 노란 줄로 찍되 `FAIL` 을 세우지 않으므로 종료 코드가
0 이다. 호출부는 함수 이름 한 단어만 바뀐다 — 분기가 아니다.

| 등급 | 뜻 | 커밋 |
|---|---|---|
| `FAIL` | 저장소나 보안 불변식을 어겼다 | 막는다 |
| `WARN` | 지금 작업하려면 손봐야 한다 | 통과한다 |
| `SKIP` | 잴 수 없었다 | 통과한다 |

여섯을 재분류했다. ollama 미기동 · 미채택 모델 · SSD 모델 잔재는 `WARN` 이다 —
느려지거나 디스크를 먹을 뿐 저장소를 틀리게 하지 않는다. 전역 훅과 SSD 비밀
파일은 `FAIL` 로 둔다 — 전자가 없으면 자격증명 검사가 통째로 안 돌고 후자는
그 자체가 노출이다.

**`THOTH_SSD_ROOT` 는 두 경우를 갈랐다.** 키가 `.env` 에 없으면 설정이 틀린
것이라 `FAIL`, 키는 있는데 경로가 없으면 마운트가 안 붙은 것이라 `WARN` 이다.
한 줄로 묶여 있어서 노트북을 도킹하지 않으면 커밋이 막히는 구조였다.

**막는 일은 실제로 필요한 자리로 옮겼다.** `run_worker.sh` 가 `ENGINE=local`
일 때 ollama 를 확인하고 없으면 기동 전에 죽는다. 띄운 뒤 502 로 알게 되면
원인을 찾는 데 시간이 들고, 실패는 그것이 일어난 자리에서 알려야 한다(§37).

`doctor` 와 `run_worker` 는 서로를 부르지 않는다. 묻는 질문이 다르다 — 전자는
"이 기계가 번역할 준비가 됐나", 후자는 "지금 워커를 띄울 수 있나" 다. 같은
판정을 두 곳에서 하는 것이 아니므로 §28 의 갈림이 아니다.

### 배운 것

**금지의 세기도 설계다.** §22 는 검사가 *어디에* 적용되는지를 정하라고 했는데,
*얼마나 세게* 적용되는지도 같은 무게로 정해야 한다. 등급이 하나면 올릴 자리가
하나뿐이라 필요 이상으로 올라간다.

그리고 **한 건을 고칠 때 같은 부류를 함께 센다.** ollama 만 고쳤으면 미채택
모델에서 같은 일이 났다. 증상 하나를 보면 그것이 유일한지 먼저 묻는다.

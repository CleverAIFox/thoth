# thoth — 결정 기록

> **같은 실수를 두 번 하지 않으려고 적는다.** 무엇을 정했는지가 아니라
> **무엇을 배웠는지**가 이 문서의 목적이다. 결과만 남는 것은 `MASTER.md`,
> 앞으로 할 일은 `PLAN.md` 에 있다.
>
> **append-only.** 이미 적힌 절은 고치지 않는다. 판단이 뒤집히면 새 절을
> 추가하고 옛 절에서 그리로 연결한다.
>
> 절 번호는 커밋 메시지가 인용한다. 지우거나 다시 매기지 않는다.
>
> 각 절은 **증상 → 원인 → 조치 → 배운 것** 순서로 적는다. "배운 것" 이 없으면
> 그 항목은 여기 올 자리가 아니다.

## §1. DOM 노드가 늘어나면 인덱스 기반 수집은 깨진다

**2026-09-12**

### 증상

선행 저장소의 수집 코드가 `document.querySelectorAll(RICH_TEXT)` 로 긁어
`[0]` 을 문제, `slice(1)` 을 보기로 잘랐다. 사전 조회 방식에서는 매칭이 실패해도
아무것도 붙지 않아 조용히 지나갔다.

### 원인

Udemy 는 채점 후 해설 노드를 같은 셀렉터로 **보기 사이에** 끼워 넣는다.
실측하니 5개에서 9개로 늘었고 순서가 문제 · 보기1 · 해설1 · 보기2 · 해설2 …
였다. `slice(1)` 은 채점 후 인덱스 2를 보기2로 취급한다.

실시간 번역으로 바꾸면 **조용한 실패가 시끄러운 오답으로 바뀐다.** 1번 보기
자리에 2번 번역이 붙는다. 학습 도구에서 이것은 없는 것보다 나쁘다.

### 조치

수집을 인덱스가 아니라 **요소 자체**로 한다. 문제 · 보기 · 해설이 각각 고유
id 를 갖는 것을 정찰에서 확인했으므로 id 로 직접 질의한다. 순서가 어떻게
섞여도 무관해진다. 계약은 MASTER §3.

### 배운 것

**정찰 30분이 오역을 막았다.** 실시간 전환 전에 채점 전후 DOM 을 둘 다 떠본
것이 결정적이었다. 한쪽만 봤으면 반대쪽에서 통째로 놓쳤다.

그리고 **동적으로 노드가 늘어나는 DOM 에서 인덱스는 식별자가 아니다.** 이것은
Udemy 만의 문제가 아니라 모든 사이트에 해당한다. 제네릭 계층도 인덱스가 아니라
요소 순회로 설계한다.

## §2. 프로세스 메모리에 둔 카운터는 Lambda 에서 무효다

**2026-09-12**

### 증상

월 문자 상한을 지키는 `guard.py` 를 모듈 전역 `_used` 로 구현했다. 로컬에서는
정확히 동작했다.

### 원인

Lambda 는 콜드스타트마다 프로세스가 새로 뜨므로 전역 변수가 0 으로 리셋된다.
동시 실행되면 인스턴스마다 따로 센다. **배포하는 순간 상한이 사실상 걸리지
않는다.**

읽고-판단하고-쓰는 순서도 문제였다. 두 요청이 같은 잔여를 보고 둘 다 통과한다.

### 조치

카운터를 DynamoDB 로 옮기고 `ConditionExpression` + `ADD` 로 조건부 원자 증가를
쓴다. 판단과 증가가 한 연산이라 경쟁이 없다. 그리고 **번역 전에 예약**한다.
실패 시 과다 계상되지만 과소 계상보다 안전하다.

### 배운 것

**로컬에서 완벽히 동작하는 코드가 실행 환경 때문에 무용지물이 될 수 있다.**
문법도 로직도 틀리지 않았고, 서버리스의 실행 모델을 알아야만 보이는 종류의
결함이다.

판단 기준이 생겼다. **상태를 어디에 두는가**를 먼저 묻는다. 캐시를 브라우저에
두면 사용자마다 재과금이고, 카운터를 프로세스에 두면 인스턴스마다 리셋이다.
이 프로젝트에서 어려웠던 것은 로직이 아니라 전부 이 질문이었다.

## §3. 파일시스템 경계를 넘는 I/O 는 값이 비싸다

**2026-09-12**

### 증상

모델 파일을 SSD(`/mnt/f`)에 두도록 `OLLAMA_MODELS` 를 설정했다. 2.4GB 모델의
첫 로딩에 **2분 12초**가 걸렸다.

### 원인

`/mnt/f` 는 DrvFs 다. Windows 파일시스템을 번역 계층을 통해 읽으므로 대용량
순차 읽기에서 네이티브 ext4 와 차이가 크다. 경로 선택의 문제가 아니라
파일시스템 경계의 문제다.

hathor D-0120(`copy2` 가 DrvFs 에서 `chmod` 로 죽는다)과 같은 계열이다.
`rsync -a` 도 `-p` 를 포함해 같은 이유로 실패한다.

### 조치

모델을 `~/.ollama`(ext4)로 되돌렸다. 그리고 **WSL 배포판 자체를 F: 로 이전**했다
(`wsl --manage --move`). vhdx 가 SSD 에 있으면서 내부는 ext4 네이티브라 두
목표를 모두 만족한다.

확장 동기화는 DrvFs 를 피할 수 없다(크롬이 네트워크 경로에서 압축해제 확장을
로드하지 못한다). 그래서 권한 보존을 끈 `rsync -rlt --no-perms --no-owner
--no-group` 을 쓴다.

### 배운 것

**"SSD 라서 빠르다" 는 파일시스템을 건너뛴 판단이다.** 물리 매체가 아니라
접근 경로가 속도를 정한다.

그리고 **DrvFs 를 피할 수 없는 경우와 피할 수 있는 경우를 나눠야 한다.**
모델 로딩은 피할 수 있고(ext4 로 옮기면 된다), 확장 로드는 피할 수 없다
(크롬 제약). 후자는 우회하지 말고 제약에 맞춰 옵션을 조정한다.

## §4. 파라미터로 모델의 성격을 이길 수 없다

**2026-09-12**

### 증상

`qwen3:4b` 에 `"think": false` 를 넘겼는데 무시했다. 번역 한 줄을 뽑으려고
수천 토큰짜리 사고를 돌렸고 **1분 28초**가 걸렸다. 출력에 `</think>` 가 그대로
찍혔다.

### 원인

qwen3 는 추론 모델이다. 사고 과정이 부가 기능이 아니라 동작 방식이라
파라미터로 끄는 것이 싸움이 된다. 번역은 추론이 필요 없는 작업인데 매번 값을
치르고 있었다.

### 조치

비추론 모델인 `exaone3.5:7.8b` 로 교체했다. 같은 작업이 2.7초다. 진 모델은
즉시 삭제하고 `doctor.sh` 가 미채택 모델을 FAIL 로 보고하도록 했다.

### 관련 발견 둘

**비결정성.** `temperature 0.2` 에서 같은 입력에 다른 출력이 나왔다. 한 번은
"접근 불가능하게 만듭니다", 다음은 "접근할 수 없게 합니다". 캐시가 최초 결과를
영구 고정하므로 흔들린 결과가 그대로 박제된다. `temperature 0` + 고정 seed 로
같은 출력을 확인했다. **결정성을 모델이 아니라 캐시가 보장하지만, 캐시에 들어갈
값이 옳은지는 별개 문제다.**

**조사 누락.** 서비스명을 영어로 두라고만 지시하니 뒤에 한국어 조사가 붙지
않아 비문이 됐다("Kinesis Data Streams 거의 즉시…"). 조사 부착을 예시와 함께
명시하니 해결됐다. 규칙 하나가 다른 규칙의 부작용을 만든다.

**답 생성.** 긴 지문에서 모델이 번역을 마친 뒤 스스로 답을 이어 붙였다. 문풀
도구에서는 정답 누설이고, 지어낸 답이 사실과 반대이기까지 했다. 프롬프트 규칙을
추가해 줄였으나 완전히 없애지 못했다(PLAN §2-2).

### 배운 것

**작업에 맞는 모델을 고르는 것이 파라미터 조정보다 먼저다.** 모델 선택이 틀리면
파라미터로 되돌릴 수 없다.

그리고 **프롬프트 규칙은 서로 간섭한다.** 규칙을 추가할 때마다 이전 규칙의
결과가 달라지는지 확인해야 한다. 이것이 골든셋이 필요한 이유다.

## §5. 휘발성 캐시는 재시작마다 재과금이다

**2026-09-12**

### 증상

`CACHE=memory` 로 개발하던 중, 코드를 고칠 때마다 워커가 재시작되면서 캐시가
비었다. 한 페이지 9개를 매번 처음부터 번역했다.

### 원인

로컬 엔진이라 비용은 시간뿐이었지만, **과금 엔진이었으면 재시작 한 번이 곧
재과금**이다. 선행 저장소에서 스크래핑 크래시로 재실행할 때마다 AWS Translate
비용이 다시 나갔던 것과 정확히 같은 구조다.

### 조치

`CACHE=file` 모드를 추가해 개발 중에도 영속 캐시를 쓴다. 배포에서는 `ddb` 다.

### 배운 것

**캐시의 영속성은 개발 편의가 아니라 비용 방어책이다.** "개발 중이니까 메모리로
충분하다" 는 판단이 배포 시점의 구조를 그대로 결정했을 수 있다.

그리고 **캐시를 어디에 두느냐가 비용 모델을 정한다.** 브라우저면 사용자마다,
프로세스면 재시작마다, 서버면 한 번이다. 선행 저장소의 `chrome.storage.local`
캐시는 사용자 10명이면 같은 문장을 10번 번역하는 구조였다.

## §6. 짧은 샘플로 잰 레이턴시는 실사용을 대표하지 않는다

**2026-09-12**

### 증상

`exaone3.5:7.8b` 벤치마크에서 2.7초가 나와 로컬 엔진 채택을 결정했다. 실제
페이지에 붙이니 **3~4분**이 걸렸다.

### 원인

벤치 문장의 출력이 26토큰이었다. 실제 문제 지문과 해설은 한국어 출력이 300토큰
가량이다. ollama 로그에 답이 있었다.

```
eval time = 2551.83 ms / 26 tokens (102.07 ms per token, 9.80 tokens per second)
```

**토큰당 시간이 지표였는데 총 시간을 봤다.** 10 tok/s × 2,700토큰 = 270초.
계산하면 나오는 값이었다.

### 조치

벤치 도구가 실제 길이의 샘플을 쓰도록 바꾸고, 실측값을 MASTER §7-1 에 토큰당
속도로 기록한다. 로컬 엔진은 실사용 불가 판정하고 호스팅 API 로 전환한다.

### 배운 것

**생성 모델의 레이턴시는 출력 길이에 비례한다. 단일 측정값이 아니라 처리율로
재야 한다.** 벤치 샘플이 실제 워크로드를 닮지 않으면 측정 자체가 거짓말이 된다.

로컬 엔진을 지우지는 않는다. 오프라인 개발용이자 비교 기준선이고,
"소비자 GPU 로는 이 워크로드가 안 된다" 는 판단의 근거 자체가 자산이다.

## §7. NMT 와 LLM 은 다른 물건이다

**2026-09-12**

### 증상

"구글 번역기는 가볍고 즉시 응답하는데 왜 이것은 4분인가" 라는 의문이 생겼다.

### 원인

구글 번역과 AWS Translate 는 LLM 이 아니라 **NMT**(신경망 기계번역) 전용
모델이다. 번역만 하는 인코더-디코더 구조이고 파라미터가 수십~수백 배 작으며,
시스템 프롬프트를 매번 처리하지 않는다.

`ENGINE=translate` 가 즉시 응답했던 것이 그 증거였다. **선행 저장소의 구조는
이미 빨랐다.**

LLM 으로 옮긴 이유는 품질이었다. NMT 는 지시를 받지 못해 "Kinesis Data
Streams" 를 "Kinesis 데이터 스트림" 으로 뭉갠다. 서비스명 보존에 AWS Custom
Terminology 같은 별도 장치가 필요하고, 그것은 AWS 전용이라 이식되지 않는다.

### 조치

품질을 택하고 속도는 하드웨어로 해결한다. 같은 모델을 데이터센터 GPU 에서
돌리면 처리율이 열 배 이상이다. **모델을 바꾸는 것이 아니라 실행 위치를
바꾸는 것**이므로 품질을 잃지 않는다.

`engine.py` 를 3분기 구조로 둔 덕분에 함수 하나 추가로 끝난다.

### 배운 것

**4분은 결함이 아니라 품질을 위해 치른 값이었다.** 원인을 "느린 코드" 로 보면
최적화할 곳을 찾게 되는데, 실제로는 교환 관계였고 지불 수단을 바꾸면 되는
문제였다.

그리고 **엔진을 환경변수로 교체 가능하게 만들어 둔 것이 이 판단을 싸게
만들었다.** 세 엔진을 같은 인터페이스에 꽂아 두었기에 비교가 가능했고, 비교가
가능했기에 근거를 갖고 고를 수 있었다.

## §8. 용어집은 커버리지가 아니라 재발 방지 장치다

**2026-09-12**

### 증상

같은 페이지 안에서 `record` 가 지문에서는 "기록", 정답에서는 "레코드" 로
번역됐다. 용어집을 도입하려 하니 "커버하지 못하는 용어가 나오면 어떻게
하는가" 라는 문제가 걸렸다.

### 원인

두 문제가 섞여 있었다.

**일관성**은 항목마다 개별 호출해 모델이 앞 문장을 모르기 때문이다. 배치
번역으로 구조가 해결한다.

**표기 선택**은 AWS 한국어 문서 관행("레코드")과 맞추는 문제다. 이것만 용어집의
몫이다.

### 조치

두 층으로 나눴다. **보편 규칙**(고유명사 유지 · 조사 부착 · 내용 추가 금지)은
프롬프트에 고정하고 도메인 지식이 0 이다. **도메인 용어집**은 JSON 파일이고
없어도 번역이 동작한다.

도메인 판정은 코드가 하지 않는다. 모든 용어집을 훑어 **원문에 실제로 나타난
용어가 가장 많은 것**을 고른다. 새 도메인은 JSON 추가로 끝난다.

### 배운 것

**룰 기반으로 100% 를 목표하면 설계가 망가진다.** 커버리지를 목표로 두면
용어집이 무한히 커지고 도메인 전용 도구가 된다.

목표를 바꿨다. **용어집은 "이미 발견한 오류의 재발 방지" 다.** `record → 기록`
을 눈으로 발견했으므로 등재했고 다시 나오지 않는다. 아직 문제되지 않은 용어는
모델 판단에 맡긴다.

그래서 **검증 가능한 불변식이 생긴다.** "등재 용어의 위반 0" 은 골든셋으로
측정되지만 "번역 정확도 100%" 는 측정 자체가 불가능하다. 측정할 수 없는 목표는
세우지 않는다.

미등재 용어의 커버리지는 사후에 자란다. 콜드패스가 실제 번역된 텍스트에서 빈출
용어를 뽑아 후보를 주고, **사람이 승인해서** 등재한다. 자동 반영하지 않는 이유는
잘못된 번역이 스스로를 강화하기 때문이다.

## §9. 세션이 바뀌는 작업은 단독 작업이 아니다

**2026-09-12**

### 증상

문서 강제자를 두지 않기로 했다. 근거는 "단독 작업이라 리뷰어가 작성자 자신"
이었다. 그런데 같은 날 `⬛` 표기 규약을 두 번 어겼다. 해결된 항목의 내용을
PLAN 에 남겨 MASTER 와 중복시켰고, 사람이 지적해서야 고쳤다.

### 원인

전제가 틀렸다. 문서를 쓰는 주체가 여러 세션에 걸쳐 있고, **세션이 바뀌면 문맥이
초기화된다.** 규약을 기억하는 주체가 연속되지 않으므로, 실제로는 여러 손이 같은
문서를 업서트하는 상황이다. 그것이 강제자가 존재하는 조건 자체다.

### 조치

`tools/check_docs.py` 를 두고 `doctor.sh` 가 부른다. 1·2인칭, 경어체 종결,
대화체 표현, DECISIONS 절의 "배운 것" 유무와 번호 연속성을 검사한다.
fire-lane 의 검사 30여 종을 옮기지 않고 문체·구조 한 종만 둔다. 규모에 맞지
않는 강제자는 유지 비용이 얻는 값을 넘는다.

검사 대상은 형식뿐이다. 내용의 옳고 그름은 사람이 본다.

### 배운 것

**"단독 작업" 의 기준은 사람 수가 아니라 문맥의 연속성이다.** 혼자 쓰더라도
작업 사이에 기억이 끊기면 협업과 같은 실패가 난다. 오랜 공백을 두고 돌아오는
프로젝트에도 같은 판단이 적용된다.

그리고 **규약을 문서에 적는 것만으로는 지켜지지 않는다.** 머리말에 규칙을
써 두었는데도 어겼다. 적는 것과 지키는 것은 다른 일이고, 지키는 쪽은 도구의
몫이다.

## §10. 기본 설정으로 돌지 않는 코드를 테스트가 가렸다

**2026-09-12**

### 증상

워커 테스트 8개가 전부 통과했다. 그런데 `.env.example` 그대로 띄우면
`/health` 와 `/translate` 가 AWS 로 나갔다. 로컬 개발에 AWS 호출이 있을
이유가 없다.

### 원인

`guard.py` 가 백엔드를 `MODE = os.environ.get("CACHE", "memory")` 로 정하고
`MODE == "memory"` 냐 아니냐로 갈랐다. `CACHE` 는 `memory` · `file` · `ddb`
세 값인데 이분법으로 가른 것이다. 현재 값인 `CACHE=file` 은 "memory 가 아님"
이므로 DynamoDB 경로로 떨어졌다.

테스트는 맨 위에서 `os.environ["CACHE"] = "memory"` 로 덮었다. **기본값이
아닌 유일한 값으로만 검증하고 있었다.** 통과한 8개는 이 결함을 구조적으로
볼 수 없었다.

여기에 두 번째 층이 겹쳤다. `main.py` 는 `QuotaExceeded` 와 `TooLong` 만
잡는다. 자격증명 없음은 그 둘이 아니므로 500 으로 흘렀고, 예외가 미들웨어를
건너뛰어 CORS 헤더가 빠졌다. §2 에 적어 둔 실패 모드가 그대로 재현됐다.

### 조치

백엔드 판정을 `REMOTE = MODE == "ddb"` 로 뒤집는다. 원격은 하나뿐이고 나머지는
로컬이라고 적는 쪽이 값이 늘어도 안 깨진다.

`file` 모드는 카운터도 파일에 남긴다. 메모리에 두면 재시작마다 월 사용량이
0 이 되어 상한이 무의미하다. 캐시와 같은 이유다(§5).

저장소에 닿지 못하는 경우를 `GuardUnavailable` 로 따로 세우고 503 으로
돌려준다. **세지 못하면 번역하지 않는다.** 통과시키면 상한이 없는 것과 같다.

테스트에 `guard.REMOTE is (guard.MODE == "ddb")` 와 file 모드 영속성을
넣었다.

### 배운 것

**열거값을 이분법으로 가르면 값이 셋이 되는 순간 조용히 틀린다.** 틀린 쪽이
기본값이면 아무도 안 밟는 경로가 아니라 모두가 밟는 경로가 된다.

그리고 **테스트가 기본 설정을 건드리지 않으면 기본 설정은 검증된 적이 없는
것이다.** 테스트를 결정적으로 만들려고 환경을 고정하는 것은 옳지만, 고정한
값이 아무도 쓰지 않는 값이면 그 테스트는 제품이 아니라 테스트 자신을 검증한다.

세 번째로 **"이미 배웠다" 와 "막았다" 는 다르다.** §2 에 CORS 오인 실패 모드를
적어 두고도 같은 실패 경로를 새로 열었다. 배운 것을 문서가 아니라 코드에
박아야 한다. 여기서는 에러 응답에 CORS 헤더가 붙는지 보는 테스트다.

## §11. 배타 선택 구조에서 상위 계층은 하위 계층보다 나빠질 수 있다

**2026-09-12**

### 증상

`standard` 어댑터가 걸린 페이지에서 보기만 번역되고 문제 지문과 본문이
통째로 빠졌다. `generic` 만 있을 때는 나왔던 것이다.

### 원인

브로커가 `priority` 내림차순으로 정렬해 `find` 로 **하나만** 고른다.
`standard` 는 `priority` 5 로 `generic` 을 이기는데, `collect` 는
`[role=radiogroup]` 안의 보기만 모은다. 이기는 순간 나머지가 사라진다.

계층을 "정확도를 높이는 장치" 로 설계했는데, 선택이 배타적이면 상위 계층은
**덧붙이는 것이 아니라 대체하는 것**이다. 설계 의도와 실행 구조가 어긋났다.

### 조치

`generic` 의 수집 로직을 `ST.genericCollect(root, {skip})` 로 꺼내
`standard` 가 자기 몫을 모은 뒤 나머지를 위임하게 했다. 상위 계층이 하위
계층을 덮지 않고 얹는다.

같이 고친 것이 하나 있다. `[role=radio]` 와 `label` 을 함께 질의하면 서로를
감싸는 쌍에서 같은 텍스트가 두 번 잡힌다. 다른 후보를 품은 요소는 버린다.

### 배운 것

**"폴백" 이라는 말이 구조를 보장하지 않는다.** Layer 0 이 항상 참이면 어디서나
동작한다는 주장은 Layer 0 이 실제로 선택될 때만 참이고, 배타 선택에서는 상위
계층이 있을 때 거짓이 된다.

판단 기준이 생겼다. **계층을 쌓을 때 선택이 배타적인지 가산적인지 먼저
정한다.** 배타라면 상위 계층은 하위 계층의 상위집합이어야 한다. 그 조건을
지킬 수 없으면 선택이 아니라 합성으로 간다.

## §12. 실패를 잊는 재시도는 재시도가 아니라 폭주다

**2026-09-12**

### 증상

번역이 실패한 자리에서 워커로 같은 요청이 1.5초마다 끝없이 나갔다.

### 원인

브로커의 `drop` 이 삽입한 박스를 걷으면서 `el.dataset.stDone` 을 지웠다.
중복 수집을 막는 표시가 사라지므로 다음 순회가 같은 유닛을 새 것으로 보고
다시 보낸다. `setInterval` 이 1.5초마다 돈다.

재시도 자체가 틀린 것은 아니다. **실패의 종류를 구분하지 않은 것**이 틀렸다.
429 상한 초과와 413 길이 초과는 같은 입력으로 다시 보내도 결과가 같다. 재시도가
상황을 바꾸지 못하는데 횟수 제한도 없었다.

실제 사용 조건에서 이것은 이론이 아니다. 5,000자를 넘는 요소가 페이지에 하나만
있어도 그 하나가 영구히 워커를 때린다.

### 조치

실패를 영구와 일시로 가른다. 클라이언트가 상태 코드를 실은 오류를 던지고,
4xx 는 영구로 본다. 영구 실패는 `dataset.stFail` 로 표시해 이 세션에서 다시
건드리지 않고, 일시 실패는 두 번까지만 재시도한다.

`quota_exceeded` 와 `guard_unavailable` 은 페이지 단위 문제가 아니므로 순회
자체를 멈춘다. 관측자와 타이머를 끊는다.

순회가 겹치지 않도록 `running` 잠금도 걸었다. `run` 이 비동기인데 타이머와
관측자가 각각 부르면 같은 배치가 두 번 나갈 수 있다.

### 배운 것

**멱등성 표시를 실패 경로에서 지우면 멱등성이 사라진다.** `stDone` 은 "처리
완료" 가 아니라 "이미 봤다" 는 뜻이어야 했다. 결과가 성공이든 실패든 본 것은
본 것이다.

그리고 **재시도를 넣을 때 종료 조건을 같이 넣지 않으면 그것은 재시도가 아니라
루프다.** 클라이언트가 상태 코드를 버리고 문자열 메시지만 던지고 있었기 때문에
브로커는 구분할 재료조차 없었다. **판단에 필요한 정보를 경계에서 버리지
않는다.**

## §13. 비동기 대기는 사용자 제스처를 끊는다

**2026-09-12**

### 증상

Udemy 외 사이트에서 아이콘을 눌러도 권한 요청 창이 뜨지 않았다.

### 원인

`chrome.permissions.request` 는 사용자 제스처 안에서 불려야 한다. 코드가
`chrome.permissions.contains` 를 먼저 `await` 하고 그 결과로 `request` 를
불렀다. 대기 한 번에 제스처 문맥이 끝나 요청이 거부된다.

`contains` 는 애초에 필요 없었다. 이미 가진 권한이면 `request` 가 창을 띄우지
않고 곧바로 참으로 해소된다.

### 조치

`request` 를 제스처 직후 첫 호출로 옮기고 `contains` 를 뺐다. 주입 실패도
같이 감쌌다 — `chrome://` · 웹스토어 · 파일 URL 은 주입이 막혀 있는데 잡지
않으면 서비스 워커 콘솔에 오류로 쌓인다.

`ST_STATIC` 의 정규식도 좁혔다. `/(^|\.)udemy\.com$/` 는 `www` 가 아닌
호스트까지 건너뛰는데 `content_scripts` 는 `www.udemy.com` 만 맡는다. 양쪽이
어긋나면 아무도 안 맡는 구멍이 생긴다.

### 배운 것

**확인을 먼저 하는 습관이 여기서는 기능을 껐다.** 방어적으로 상태를 조회하고
분기하는 것이 일반적으로는 옳지만, 호출 자체에 시간 제약이 걸린 API 에서는
조회가 비용이 아니라 실패 원인이다.

그리고 **한 가지 사실을 두 곳에 적으면 어긋난다.** manifest 의 매치 패턴과
배경 스크립트의 제외 목록이 같은 사실을 다른 문법으로 적고 있었다. 지금은
주석으로 묶어 두었지만, 구조적으로는 한쪽에서 읽어 쓰는 쪽이 옳다.
